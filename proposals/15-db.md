# Proposal: `daemon/db.py`

Date: 2026-04-13

## Goal

Define the design for `daemon/db.py` as the SQLite database layer for
the Humility Discord daemon.

This proposal is design only. It does not include implementation code.

## Summary

`daemon/db.py` should be a small, synchronous SQLite module with three
jobs:

- resolve the database path from configuration
- open and configure a file-backed `sqlite3` connection
- expose plain query helpers for the four daemon tables

For v1, the module should stay scaffold-only and bootstrap-first:

- use stdlib `sqlite3`, not an ORM
- set `row_factory = sqlite3.Row` on every connection
- enable WAL mode for the shared daemon/CLI database file
- create the four schema tables with `CREATE TABLE IF NOT EXISTS`
- keep helper functions table-oriented and parameterized
- avoid workflow logic, Discord calls, and policy decisions

The module should not try to solve migrations, status-transition rules,
or a full repository abstraction in the first pass.

## Data Model

The canonical persisted model is the four tables already defined in
`docs/DAEMON_DESIGN.md`. `daemon/db.py` should treat those tables as the
source of truth and should not introduce a second object model on top of
them.

### Connection Model

The runtime connection model should be intentionally simple:

- one SQLite database file
- one long-lived daemon connection for normal runtime use
- one short-lived connection per CLI invocation
- `sqlite3.Row` as the default row shape for all reads

Rows should remain `sqlite3.Row` objects rather than custom model
instances. That keeps the layer thin and avoids ORM-style drift.

### `DatabaseConfig`

The module should define one small configuration object.

Fields:

- `path: Path`

Behavior:

- the path comes from `DATABASE_PATH` when set
- otherwise the local-development default is `discord.db`
- Railway should continue to supply `/data/discord.db` through
  `DATABASE_PATH`, not through a hardcoded production branch in code

### Persisted Tables

#### `chapters`

Purpose:

- stores chapter provisioning metadata persisted after daemon-side
  chapter creation

Key shape:

- primary key: `slug`
- active/archive state is represented by nullable `archived_at`

Notes:

- `form_path` stays as stored text
- no foreign-key enforcement is added in v1

#### `submissions`

Purpose:

- stores application submissions and their queue/thread lifecycle state

Key shape:

- primary key: autoincrement `id`
- lifecycle state is tracked by `status`

Notes:

- `answers_json` remains serialized JSON text
- queue and decision fields are nullable because they are populated over
  time

#### `tickets`

Purpose:

- stores server, mod, and chapter ticket records

Key shape:

- primary key: autoincrement `id`
- lifecycle state is tracked by `status`

Notes:

- `chapter_slug` is nullable for non-chapter tickets
- closure metadata is nullable until a ticket is closed

#### `chapter_blacklist`

Purpose:

- stores per-chapter application blacklist entries

Key shape:

- composite primary key: `(chapter_slug, user_id)`

Notes:

- this table is intentionally small and lookup-oriented

## Connection And Bootstrap

The module should separate opening a connection from bootstrapping the
schema.

### Connection Rules

When `daemon/db.py` opens a connection, it should:

- use a file-backed SQLite database path
- set `row_factory = sqlite3.Row`
- rely on parameterized SQL for every query helper

The connection object itself should remain a raw `sqlite3.Connection`.
The module does not need a wrapper class for v1.

### Bootstrap Rules

Bootstrap should be explicit and idempotent.

The bootstrap routine should:

- execute `PRAGMA journal_mode=WAL;`
- run one schema script containing `CREATE TABLE IF NOT EXISTS` for:
  - `chapters`
  - `submissions`
  - `tickets`
  - `chapter_blacklist`

For v1, bootstrap should stop there. It should not add a migration
framework, schema diffing, or compatibility repair logic.

## Public API

`daemon/db.py` should expose a small function-first API surface.

### `resolve_database_config(env: Mapping[str, str] | None = None) -> DatabaseConfig`

Responsibilities:

- read `DATABASE_PATH` from a supplied environment mapping
- default to `discord.db` when the variable is absent
- return a typed config object rather than a bare string

This keeps environment reads centralized and testable.

### `connect_database(path: Path) -> sqlite3.Connection`

Responsibilities:

- open the SQLite database file
- configure the connection for daemon use
- set `row_factory = sqlite3.Row`

This function should not create tables implicitly. Opening a connection
and bootstrapping schema should remain separate steps.

### `bootstrap_database(conn: sqlite3.Connection) -> None`

Responsibilities:

- enable WAL mode
- run the idempotent four-table bootstrap script

This function may be called on both daemon startup and CLI startup
without harming an already-initialized database.

### Query Helper Shape

All table helpers should follow the same rules:

- plain functions, not classes
- `conn` as the first argument
- explicit scalar parameters rather than opaque dict payloads
- parameterized SQL only
- return `sqlite3.Row`, `list[sqlite3.Row]`, `int`, `bool`, or `None`
  depending on the query
- no implicit `commit()` inside helpers; transaction boundaries belong
  to the caller

### V1 Helper Families

The module should reserve helper families for all four tables, but the
first implementation pass only needs the foundational subset required by
startup and the earliest daemon/CLI consumers.

#### `chapters`

Planned helper family:

- `insert_chapter(...)`
- `get_chapter_by_slug(conn, slug)`
- `list_active_chapters(conn)`
- `archive_chapter(conn, slug, archived_at)`

#### `submissions`

Planned helper family:

- `create_submission(...)`
- `get_submission_by_id(conn, submission_id)`
- `get_submission_by_thread_id(conn, thread_id)`
- `get_submission_by_queue_message_id(conn, queue_message_id)`
- `update_submission_queue_refs(...)`
- `update_submission_status(...)`
- `list_submissions(...)`

#### `tickets`

Planned helper family:

- `create_ticket(...)`
- `get_ticket_by_id(conn, ticket_id)`
- `get_ticket_by_thread_id(conn, thread_id)`
- `get_ticket_by_queue_message_id(conn, queue_message_id)`
- `update_ticket_queue_refs(...)`
- `update_ticket_status(...)`
- `list_tickets(...)`

#### `chapter_blacklist`

Planned helper family:

- `add_blacklist_entry(...)`
- `get_blacklist_entry(conn, chapter_slug, user_id)`
- `list_blacklist_entries(conn, chapter_slug)`
- `remove_blacklist_entry(conn, chapter_slug, user_id)`

Design note:

- this proposal defines the helper surface now so later CRUD expansion is
  additive and predictable
- v1 implementation should prioritize connection/bootstrap plus the
  minimum helpers actually needed by the first daemon flows

## Anti-scope

`daemon/db.py` should not contain:

- an ORM, model base class, repository abstraction, or unit-of-work
  framework
- Discord API calls, slash-command handlers, modal handling, claim
  logic, or ticket/application workflow code
- config-file loading from YAML; that remains in `daemon/config.py`
- business-rule enforcement for valid status transitions
- JSON schema validation for `answers_json`
- automatic role changes, DMs, thread membership updates, or queue post
  creation
- a migration framework, `ALTER TABLE` orchestration, or schema repair
  logic in v1
- hidden global connections, connection pooling, or background DB
  workers
- ad hoc one-off SQL scripts outside the module’s query-helper surface

## Decision

Treat `daemon/db.py` as a thin SQLite boundary: resolve the database
path, open a configured connection, bootstrap the four-table schema, and
offer plain per-table query helpers. Keep the module synchronous,
table-oriented, and intentionally boring so the daemon and CLI can share
one stable database layer without pulling interaction logic into it.
