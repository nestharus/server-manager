# Kubernetes Manifest Layer Research for Phase 1

Research date: 2026-04-14

## 1. Scope and context

This report covers the manifest-layer problem space for four Kubernetes
entry points that this repository will add or complete for a Phase 1
foundation deployment:

1. `k8s/base/flux-system/kustomization.yaml`
2. `k8s/base/monitoring/helmrelease.yaml`
3. `k8s/base/secrets/helmrelease.yaml`
4. `k8s/overlays/staging/kustomization.yaml`

Locked stack for this research:

- GitOps controller: Flux CD
- Cluster distro: k3s
- Infra provisioning: kube-hetzner via OpenTofu
- Monitoring: `kube-prometheus-stack`
- Bootstrap secrets: Bitnami `sealed-secrets`
- Future secret management: Infisical, explicitly out of scope for this phase

Existing repo context already establishes:

- `k8s/base/monitoring/` with `namespace.yaml`, `helmrepository.yaml`,
  and `kustomization.yaml`
- `k8s/base/secrets/` with `namespace.yaml`, `helmrepository.yaml`, and
  `kustomization.yaml`
- empty or incomplete directories for `k8s/base/flux-system/`,
  `k8s/overlays/staging/`, and `k8s/overlays/production/`

This is Phase 1 research only. It does not propose manifest content or
YAML structure beyond documenting what the official docs and chart
sources say, plus clearly labeled inference where upstream is silent.

## 2. Flux Bootstrap Root Kustomization

### Confirmed facts

#### Bootstrap artifacts and root entry point role

Flux bootstrap documentation and Flux bootstrap customization docs show
that bootstrap creates a repository path containing three files:

| Artifact | Confirmed role | Source |
|---|---|---|
| `gotk-components.yaml` | Flux controller install manifests | [Flux bootstrap customization](https://fluxcd.io/flux/installation/configuration/bootstrap-customization/) |
| `gotk-sync.yaml` | Sync-related manifests generated by bootstrap | [Flux bootstrap customization](https://fluxcd.io/flux/installation/configuration/bootstrap-customization/) |
| `kustomization.yaml` | Root Kustomize entry point that includes the other two files as resources | [Flux bootstrap customization](https://fluxcd.io/flux/installation/configuration/bootstrap-customization/) |

Flux bootstrap for Git servers documents the same file set and shows the
canonical bootstrap path pattern as `clusters/<cluster>/flux-system/`.
It also documents that bootstrap deploys Flux controllers onto the
cluster and configures them to sync from Git. The Git credentials secret
is stored as a Kubernetes Secret named `flux-system` in the
`flux-system` namespace. See:

- [Flux bootstrap for Git servers](https://fluxcd.io/flux/installation/bootstrap/generic-git-server/)
- [Flux bootstrap for GitHub](https://fluxcd.io/flux/installation/bootstrap/github/)

#### What a root GitOps entry point typically references

Flux’s repository-structure guide documents a common monorepo layout
with `apps/`, `infrastructure/`, and `clusters/`, where cluster
directories define which app and infrastructure overlays belong to a
particular environment. Flux’s official framing is that separating apps
and infrastructure helps define reconciliation order. See:

- [Ways of structuring your repositories](https://fluxcd.io/flux/guides/repository-structure/)

That means there are two distinct “root” concepts in Flux repos:

| Root concept | Confirmed behavior | Source |
|---|---|---|
| Bootstrap root | The `kustomization.yaml` committed by bootstrap includes `gotk-components.yaml` and `gotk-sync.yaml` | [Flux bootstrap customization](https://fluxcd.io/flux/installation/configuration/bootstrap-customization/) |
| Cluster/environment root | A Flux `Kustomization` object points at a repo path and reconciles the `kustomization.yaml` found there | [Flux FAQ](https://fluxcd.io/flux/faq/), [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |

#### Namespace practices for `flux-system`

Official Flux bootstrap docs consistently use `flux-system` as both:

- the namespace containing bootstrap-managed Flux resources
- the name of the Git credentials Secret created by bootstrap

The bootstrap examples and generated file structure are built around
that namespace. See:

- [Flux bootstrap for GitHub](https://fluxcd.io/flux/installation/bootstrap/github/)
- [Flux bootstrap for Git servers](https://fluxcd.io/flux/installation/bootstrap/generic-git-server/)
- [Flux bootstrap customization](https://fluxcd.io/flux/installation/configuration/bootstrap-customization/)

#### Reconciliation and dependency patterns

The Flux `Kustomization` API documents these controller-level behaviors
as relevant to a root entry point:

| Field or behavior | Confirmed role | Source |
|---|---|---|
| `.spec.interval` | Required reconciliation cadence | [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |
| `.spec.path` | Directory in the source artifact containing the overlay or manifests | [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |
| `.spec.prune` | Required garbage-collection switch | [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |
| `.spec.dependsOn` | Dependency ordering between Flux `Kustomization` objects | [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |
| `.spec.wait` and `.spec.healthChecks` | Health-gated reconciliation | [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |
| `.spec.timeout` and `.spec.retryInterval` | Failure and retry behavior | [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |

Flux FAQ also documents that reconciliation means building the Kustomize
overlay, validating, applying, health-checking, and pruning removed
resources, and that Flux will revert drift from `kubectl edit` on the
next reconciliation. See:

- [Flux FAQ](https://fluxcd.io/flux/faq/)

Flux FAQ further advises against Kustomize remote bases for security and
performance reasons and notes that admins can enforce
`--no-remote-bases=true` in `kustomize-controller`. See:

- [Flux FAQ](https://fluxcd.io/flux/faq/)

### Inference

The repo path `k8s/base/flux-system/` is not the same path shape Flux
uses in its bootstrap examples, which use `clusters/<cluster>/flux-system/`.
That does not make the repo layout wrong, but it does mean this repo is
choosing a local convention rather than following Flux’s default
generated path literally.

Because Flux docs consistently center `flux-system` as the namespace,
Secret name, and bootstrap directory name, keeping `flux-system`
canonical minimizes divergence from the bootstrap toolchain. Changing
that namespace is possible in Kubernetes terms, but it raises local
complexity because the defaults, examples, and generated artifacts all
assume `flux-system`.

For this repo, the unresolved research question is whether
`k8s/base/flux-system/kustomization.yaml` is intended to be:

- only the bootstrap artifact aggregator, or
- a broader platform root that later composes other bases

Flux’s docs support both a bootstrap root and a cluster/environment
root, but they are not the same layer.

### Inference

Upstream leaves most resource requests and limits either empty or
unstated for this chart, so there is no official small-cluster budget to
copy for a 1-3 node k3s deployment. For Phase 1 research, the safest
conclusion is not “the defaults are small-cluster ready,” but “the
operator must choose explicit budgets because upstream does not impose
them.”

For a small k3s cluster, the relative pressure points are clear even
without an official sizing table:

| Component | Small-cluster implication |
|---|---|
| Prometheus | Dominant disk and memory consumer; retention and PVC policy are the primary cost drivers |
| Alertmanager | Usually much lighter than Prometheus, but persistence still matters if silence/history durability matters |
| Grafana | Usually secondary in CPU and memory, but persistence choice changes whether local state survives pod replacement |
| node-exporter | One pod per node, so footprint scales linearly from 1 to 3 nodes |
| kube-state-metrics and operator | Typically smaller than Prometheus, but still need explicit resource caps because chart defaults do not enforce them |

The default persistence posture is effectively “bring your own durable
storage settings.” An empty `storageSpec` for Prometheus and empty
`storage` for Alertmanager do not answer the Phase 1 question of whether
metrics and alert state must survive rescheduling. Likewise, Grafana’s
default `persistence.enabled: false` means upstream does not assume
durable local Grafana state.

For staging specifically, reduced retention and reduced resource budgets
are reasonable environment-level patch categories, but upstream does not
publish a canonical staging profile for this chart. Any such profile is
an environment inference, not a documented chart default.

### Inference

Because this repo already treats sealed-secrets as a temporary Phase 1
bootstrap mechanism and explicitly plans to replace it later with
Infisical, the research boundary is narrower than for a long-term
secrets platform.

For that temporary role, the highest-value concerns are:

- controller availability
- correct namespace and RBAC placement
- recoverability of sealing keys
- avoiding drift that complicates later removal

By contrast, ingress exposure, extra metrics integration, aggressive
custom naming, or elaborate controller tuning are not required by the
bootstrap problem itself. They may be valid later, but the upstream docs
do not make them bootstrap necessities.

The other major constraint is lifecycle cost. Since sealed-secrets keys
renew over time and backups must be refreshed after renewal, even a
“temporary” Phase 1 installation creates an operational obligation until
Infisical actually replaces it.

### Confirmed facts

#### How Kustomize overlays compose bases

| Mechanism | Confirmed behavior | Source |
|---|---|---|
| `resources` | Includes base manifests or other resource paths | [Kubernetes Kustomize docs](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/) |

#### Flux-compatible overlay behavior and constraints

Flux FAQ and Flux `Kustomization` docs establish these constraints:

| Constraint | Confirmed behavior | Source |
|---|---|---|
| Path rendering | A Flux `Kustomization` points at a directory path and reconciles the `kustomization.yaml` found there | [Flux FAQ](https://fluxcd.io/flux/faq/), [Kustomization docs](https://fluxcd.io/flux/components/kustomize/kustomizations/) |
| Explicit Kustomize vs generated Kustomize | If no `kustomization.yaml` exists, Flux can generate one, but explicit overlays are supported directly | [Flux FAQ](https://fluxcd.io/flux/faq/) |
| Drift correction | Manual `kubectl edit` changes are reverted by reconciliation | [Flux FAQ](https://fluxcd.io/flux/faq/) |
| Prune behavior | With pruning enabled, removing or moving resources can delete them unless migration is handled carefully | [Flux FAQ](https://fluxcd.io/flux/faq/) |
| Remote bases | Flux advises against Kustomize remote bases for security and performance reasons | [Flux FAQ](https://fluxcd.io/flux/faq/) |

Flux also distinguishes between:

- the Kubernetes/Kustomize file `kustomization.yaml`
- the Flux CRD `kustomize.toolkit.fluxcd.io/Kustomization`

See:

- [Flux FAQ](https://fluxcd.io/flux/faq/)

### Inference

For `k8s/overlays/staging/kustomization.yaml`, the most plausible
staging-only patch categories are environment deltas rather than
structural rewrites. Based on the upstream docs and chart defaults, the
main categories are:

| Category | Why it is staging-shaped rather than base-shaped |
|---|---|
| Reduced resource requests and limits | Upstream chart defaults often leave resources open-ended, while staging usually has smaller capacity budgets |
| Smaller retention windows | Monitoring storage cost is strongly environment-sensitive |
| Smaller or no persistent volumes | Staging durability expectations are often lower than production |
| Reduced replica counts or HA settings | HA is chart-supported but not equally necessary in staging |
| Exposure differences | Grafana or Alertmanager ingress and service exposure commonly differ by environment |
| Reconciliation cadence differences | Flux supports interval changes, but shorter intervals also increase churn and controller activity |

The key Flux-specific constraint is that staging overlays should remain
local and explicit. Remote bases are discouraged by Flux, and moving
resources between different Flux `Kustomization` ownership boundaries is
prune-sensitive.

Another practical implication is ownership clarity. If staging overlays
only patch environment-specific differences, Flux reconciliation remains
more predictable. If staging begins to redefine structure rather than
patch it, the overlay stops being a thin environment layer and becomes a
parallel manifest tree.

## 6. Cross-Cutting Constraints and Open Questions

### Cross-cutting constraints

| Constraint | Why it matters in this repo |
|---|---|
| Flux bootstrap path conventions differ from this repo’s `k8s/base/...` layout | The repo is not using Flux’s generated `clusters/<cluster>/flux-system/` shape literally, so path ownership needs to stay explicit |
| Flux has two “Kustomization” layers | The repo must keep file-level Kustomize overlays separate from Flux CRD reconciliation objects conceptually |
| Upstream monitoring docs do not give a 1-3 node k3s sizing profile | Small-cluster resource numbers will require local judgment, not copy-paste from official docs |
| `kube-prometheus-stack` leaves several resource blocks empty by default | Default chart behavior is not the same as a deliberate small-cluster budget |
| Monitoring persistence defaults are incomplete for durable operations | Prometheus, Alertmanager, and Grafana persistence expectations are a Phase 1 architecture question, not something upstream decides automatically |
| Sealed-secrets creates an ongoing key-backup obligation until replacement | Temporary bootstrap still creates recurring operational work |
| Flux prune behavior makes manifest moves and renames sensitive | Overlay and ownership boundaries matter early, not only later |

### Open questions

1. Is `k8s/base/flux-system/` intended to hold only bootstrap artifacts,
   or will it also aggregate deeper platform bases?
2. Which Flux object will reconcile the `k8s/overlays/staging/` path,
   and is that object separate from the bootstrap-managed `flux-system`
   sync object?
3. What is the required durability level for Prometheus, Grafana, and
   Alertmanager in Phase 1 staging versus production?
4. Which storage class behavior is expected from the k3s cluster for
   Prometheus and Alertmanager PVCs? This report does not cover storage
   class implementation details.
5. Does staging need shorter Flux reconciliation intervals, or only
   smaller application-level budgets such as retention and resources?
6. Who owns sealed-secrets key backup and restoration during the period
   before Infisical exists?
7. When Infisical replaces sealed-secrets, will sealed-secrets remain
   only long enough to migrate existing encrypted bootstrap material, or
   longer as a compatibility layer? This report assumes no compatibility
   shim, but the migration sequence still affects Phase 1 boundaries.
