Date: 2026-04-13

This note documents the current problem space for the planned
`daemon/db.py` module.

- what the repo says `db.py` is responsible for
- what Python `sqlite3` and SQLite expose for this kind of module

interaction flow logic beyond what the design doc already specifies.

## 1. What `sqlite3` provides for this module

Python’s stdlib `sqlite3` module is a synchronous DB-API 2.0 interface
to SQLite. That matches the daemon design note that `db.py` uses
synchronous `sqlite3`, not an async wrapper.

Relevant capabilities from the Python 3.12 docs:

- `sqlite3.connect()` opens a file-backed database connection from a
  path-like object.
- The default connect timeout is 5 seconds when a table is locked.
- `Connection.execute()` and `executemany()` run parameterized SQL.
- `Connection.executescript()` runs multiple SQL statements in one call.
- `sqlite3` supports qmark (`?`) and named (`:name`) placeholders.
- The docs explicitly say to use placeholders instead of string
  formatting to avoid SQL injection.
- The default row representation is a tuple.
- `sqlite3.Row` provides indexed and case-insensitive named column
  access.
- `Connection.row_factory` can be set once so all cursors inherit the
  same row shape.

Local observations in this repo:

- `con.row_factory` defaults to `None`.
- Setting `con.row_factory = sqlite3.Row` returns row objects with both
  index and column-name access.
- `Connection.__enter__/__exit__` supports transaction-scoped context
  manager use; the local `pydoc` output states success commits and
  exceptions roll back.

Why this matters for the daemon problem space:

- The schema has several read-heavy lookup cases where named-column
  access is easier to reason about than positional tuples.
- The schema includes user-provided fields such as `subject`,
  `initial_description`, `decision_reason`, and `answers_json`, so
  parameterized queries are directly relevant.
- The full schema bootstrap is four `CREATE TABLE` statements, so the
  available `executescript()` primitive is directly relevant.

## 2. WAL mode and related SQLite pragmas

The daemon design explicitly calls for SQLite on a persistent on-disk
database file, and the user asked to research WAL mode.

Official SQLite WAL facts:

- SQLite defaults to rollback-journal `DELETE` mode.
- WAL mode is enabled with `PRAGMA journal_mode=WAL;`.
- On success, that pragma returns `wal`; on failure it returns the prior
  mode unchanged.
- WAL mode is persistent for the database file once set.
- WAL improves concurrency because readers do not block writers and a
  writer does not block readers, although there is still only one writer
  at a time.
- WAL uses automatic checkpointing by default once the WAL reaches 1000
  pages.
- `PRAGMA wal_autocheckpoint` and `PRAGMA wal_checkpoint` exist if the
  application needs to inspect or alter checkpoint behavior.

Related local observations:

- `PRAGMA busy_timeout` reports `5000` on a new local connection, which
  matches the Python connect default of 5 seconds.

Why this matters here:

- The design says the daemon and CLI share one database file, so the
  concurrency model is not purely single-connection.
- Railway’s `/data/discord.db` is a local persistent volume path, which
  matches WAL’s same-host requirement.

## 3. Bootstrap and migration primitives

The design doc gives a complete four-table schema today
([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:103)).
That creates two distinct problem categories:

- first-boot schema creation
- later schema evolution on an existing database file

Relevant primitives from SQLite and Python docs:

- `CREATE TABLE IF NOT EXISTS` is idempotent for first creation; if a
  table of the same name already exists, the statement has no effect.
- `executescript()` can run a multi-statement schema bootstrap script.
- `PRAGMA user_version` is an application-defined integer stored in the
  database header; SQLite does not assign meaning to it.
- `PRAGMA table_info` and `PRAGMA table_list` exist for schema
  inspection.

Direct consequence from those primitives:

- `CREATE TABLE IF NOT EXISTS` is enough to make initial table creation
  repeatable.
- It does not, by itself, reconcile changed column definitions, new
  indexes, renamed columns, or other schema drift, because an existing
  table causes the statement to no-op.
- SQLite exposes an application-owned version slot (`user_version`) that
  can be used to distinguish database schema revisions, but the policy
  for how migrations are organized is not specified anywhere in the repo
  yet.

One version-sensitive point from Python 3.12 docs:

- `executescript()` implicitly commits any pending transaction before
  running the script under legacy transaction control.
- Python 3.12 also moves transaction guidance toward the
  `Connection.autocommit` attribute; the default remains legacy
  transaction control for now, but the docs say the default will change
  in a future Python release.

That means migration behavior depends partly on whether the daemon
chooses legacy transaction handling or explicit autocommit settings.

## 4. Connection management in a long-running daemon

The design doc describes one always-on daemon process plus occasional
CLI invocations that share the same on-disk database
([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:3),
[docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:193)).

Facts from the Python docs that matter to that setup:

- A `Connection` object represents one open database connection.
- Pending writes are not durable until committed.
- With Python 3.12 transaction guidance, explicit `commit()` and
  `rollback()` calls are part of the normal control surface.
- Closing a connection with pending changes performs an implicit
  rollback.
- The connection context manager commits on success and rolls back on
  exception, but it does not close the connection.
- `timeout` and `busy_timeout` are the built-in first-line behavior when
  another connection currently holds a write lock.

Repo-specific implications:

- A long-running daemon can keep one connection open for a long period.
- One-shot CLI commands can open separate short-lived connections against
  the same file.
- The design doc does not mention a connection pool, per-request
  connection factory, or multi-database setup; the problem space is one
  SQLite file with at least two process entrypoints.

## 5. Thread-safety constraints

There are two separate thread-safety layers in play:

- the underlying SQLite library threading mode
- Python’s per-connection `check_same_thread` behavior

Python 3.12 `sqlite3` facts:

- `sqlite3.threadsafety` is derived from the SQLite library build.
- In serialized mode, the DB-API `threadsafety` value is `3`, meaning
  threads may share the module, connections, and cursors.
- `sqlite3.connect(..., check_same_thread=True)` is still the default.
- With that default, using a connection from a different thread raises
  `ProgrammingError`.
- If `check_same_thread=False`, Python allows cross-thread connection
  use, but the docs say write operations may need application-side
  serialization to avoid corruption.

Local observations:

- Both local runtimes in this repo report `sqlite3.threadsafety == 3`.
- A direct thread hop with the default connection settings raised:
  `ProgrammingError: SQLite objects created in a thread can only be used in that same thread.`

Why this matters here:

- The daemon is long-running and may eventually use background tasks,
  worker threads, or callback paths that are not all on the creating
  thread.
- The design doc does not state whether database access stays on one
  thread, uses one connection per thread, or deliberately disables
  `check_same_thread`.
- That choice affects the safe connection-management envelope, even
  though the current design does not require async database code.

## 6. Query helper surface implied by the current schema

The schema itself appears in
[docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:105).
The interaction flow and admin workflow define the minimum database
operations implied by that schema today.

### `chapters`

Directly implied operations:

- insert chapter metadata when chapter provisioning completes
  ([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:71))
- fetch chapter metadata by `slug`
- list active chapters for runtime lookups
- mark a chapter archived by setting `archived_at`, because the schema
  includes that field and the design includes a chapter archive flow
  ([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:73))

Notable schema facts:

- `slug` is the primary key.
- Discord object IDs are stored as `INTEGER`.
- the form reference is stored as `form_path TEXT`, not a foreign key.

### `submissions`

Directly implied operations:

- create a new submission row when an application is finally submitted
- persist queue message, queue channel, and thread IDs after Discord-side
  objects are created
- fetch a submission by `id`
- fetch by `thread_id` or `queue_message_id` for button/action handlers
- move status through at least `pending`, `claimed`, `interview`,
  `approved`, `denied`, and `withdrawn`
- set `claimer_id` on claim
- set `decided_by`, `decided_at`, and `decision_reason` on approval or
  denial
- list submissions for CLI inspection, because "list submissions" is
  explicitly called out as a CLI responsibility
  ([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:196))

Notable schema facts:

- `answers_json` is stored as `TEXT`, so the schema treats application
  answers as one serialized payload rather than normalized child rows.
- There are no declared foreign keys tying `chapter_slug` to
  `chapters.slug`.

### `tickets`

Directly implied operations:

- create a new ticket row when `/ticket <category>` is submitted
- persist queue message, queue channel, and thread IDs
- fetch a ticket by `id`
- fetch by `thread_id` or `queue_message_id` for button/action handlers
- claim a ticket by setting `status` and `claimer_id`
- close a ticket by setting `status`, `closed_at`, and `closed_by`
- inspect tickets by status and type for daemon or CLI visibility

Notable schema facts:

- `ticket_type` encodes four current categories:
  `server`, `mod`, `chapter_support`, `chapter_incident`.
- `chapter_slug` is nullable because server/mod tickets are not tied to
  a chapter.

### `chapter_blacklist`

Directly implied operations:

- check whether `(chapter_slug, user_id)` exists before `/apply`
  ([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:79))
- add a blacklist row with `reason`, `added_by`, and `added_at`
  ([docs/DAEMON_DESIGN.md](/home/nes/discord/docs/DAEMON_DESIGN.md:81))

Schema facts that affect helper behavior:

- `(chapter_slug, user_id)` is the primary key, so duplicate add
  behavior is constrained by the schema even though the user-facing
  policy is not yet described.
- The design doc mentions add/check behavior explicitly, but does not
  yet mention remove or list operations.

## 7. Schema characteristics that the DB layer will have to account for

These are not solution proposals; they are properties of the current
schema that shape the DB problem space:

- There are no explicit `FOREIGN KEY` constraints in any of the four
  tables.
- There are no indexes beyond the primary keys shown in the schema.
- All timestamps are stored as `TEXT`, not native Unix timestamps.
- Discord snowflakes are stored as `INTEGER`.
- The schema uses status strings rather than separate lookup tables or
  enum types.
- The schema currently omits any migration bookkeeping table; the only
  built-in SQLite version slot exposed by the docs is `PRAGMA
  user_version`.

## Bottom Line

The current problem space for `daemon/db.py` is a conventional
single-file SQLite layer for one long-running process plus occasional
CLI access. The main technical questions are not whether stdlib
`sqlite3` can do the work; it can. The real boundaries are:

- how the module separates first-run bootstrap from later schema
  evolution
- how it manages one or more connections over a long-lived daemon
  lifetime
- how it stays inside sqlite3’s thread and transaction rules
- how much query-helper surface it exposes for the four tables without
  absorbing higher-level application flow logic
