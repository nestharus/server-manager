## Touched surface

- `migrations/versions/wu-011_members.py`: the `members` table is defined with `id`, `discord_user_id`, `joined_at`, `status`, timestamps, a unique constraint on `discord_user_id`, and a status check constraint, but no identity-kind discriminator today (`migrations/versions/wu-011_members.py:16-43`). INIT-125A needs a migration that adds `kind TEXT NOT NULL`, backfills `public:%` rows to `public_intake` and all other rows to `discord`, and adds a check constraint for `('discord', 'public_intake')`.
- `services/api/app/repositories/members.py`: `_MEMBER_SELECT` must select `m.kind` so service guard helpers can inspect it from fetched rows (`services/api/app/repositories/members.py:10-22`). `_insert_member()` is the only production SQL insert helper for `members`; it currently inserts `id`, `discord_user_id`, `joined_at`, and `status` only (`services/api/app/repositories/members.py:58-79`).
- `services/api/app/services/members.py`: `SYNTHETIC_MEMBER_PREFIX` and `is_synthetic_member()` currently define synthetic identity by `discord_user_id.startswith("public:")` (`services/api/app/services/members.py:46-56`). `_member_from_row()` must include `kind` when constructing `MemberRead` (`services/api/app/services/members.py:87-96`). `create_or_get_member()` is the normal member creation path and currently passes no discriminator into `_insert_member()` (`services/api/app/services/members.py:116-177`). `resolve_or_create_public_intake_member()` derives `discord_user_id="public:<digest>"` and calls `create_or_get_member()` as the public-intake service actor (`services/api/app/services/members.py:180-206`). `patch_member_status()` is an INIT-124 guard site and currently checks the prefix before status mutation (`services/api/app/services/members.py:229-295`).
- `services/api/app/contracts/members.py`: `MemberRead` currently exposes `id`, `discord_user_id`, `joined_at`, `status`, timestamps, and version, but no `kind` (`services/api/app/contracts/members.py:25-32`). If `kind` is part of the stable member contract, add a `MemberKind = Literal["discord", "public_intake"]` and include it in `MemberRead`. `MemberCreate` does not need caller-supplied `kind`; normal API creation can remain inherently `discord` (`services/api/app/contracts/members.py:18-22`).
- `services/api/app/services/applications.py`: `_require_non_synthetic_application_member()` guards owner-like member ids using the current prefix predicate (`services/api/app/services/applications.py:324-336`). Authenticated submit rejects synthetic applicants unless the internal authority is `PUBLIC_INTAKE` (`services/api/app/services/applications.py:618-632`). Public submit is the approved exception: it resolves/creates a public-intake member and calls `_submit_application_internal(..., submission_authority=_SubmissionAuthority.PUBLIC_INTAKE)` (`services/api/app/services/applications.py:773-805`). Owner guard call sites are claim actor, reassign owner, and reactivate owner (`services/api/app/services/applications.py:867-907`).
- `services/api/app/services/trust.py`: `create_trust_signal()`, `compute_trust()`, and `_recompute_once()` each fetch the member and reject prefix-classified synthetic subjects before mutating trust state (`services/api/app/services/trust.py:291-321`, `services/api/app/services/trust.py:384-397`, `services/api/app/services/trust.py:474-486`).
- `services/api/app/services/roster.py`: `_validate_roster_member()` parses UUID-like roster member ids, fetches the member row, and rejects prefix-classified synthetic members before roster insert (`services/api/app/services/roster.py:120-137`). `create_roster_entry()` calls this validator immediately before `_insert_roster_entry()` (`services/api/app/services/roster.py:139-158`).
- `services/api/app/services/authority.py` and `services/api/app/services/read_models.py`: `_resolve_member_aliases()` / `_collect_member_aliases()` are the leadership alias guard surface; they currently reject or omit synthetic rows after fetching a member by UUID and checking the prefix (`services/api/app/services/authority.py:145-182`, `services/api/app/services/authority.py:185-201`). Direct leadership context uses `synthetic_policy="reject"` (`services/api/app/services/read_models.py:247-252`), while succession-plan handoff aggregation uses `synthetic_policy="omit"` (`services/api/app/services/authority.py:549-553`).
- `services/api/tests`: synthetic-member fixtures and expectations are prefix-based today. The shared factory directly inserts `members` with no `kind` column and creates synthetic fixtures as `public:<uuid hex>` (`services/api/tests/conftest.py:198-233`). The unit predicate test is explicitly named `test_is_synthetic_member_identifies_only_public_prefix` and parametrizes raw strings / objects with `discord_user_id` values (`services/api/tests/test_synthetic_member_helper.py:10-54`). Public-intake tests assert the generated `discord_user_id` matches `public:[0-9a-f]{32}` and public submit readbacks start with `public:` (`services/api/tests/test_public_intake_synthetic_member.py:37-45`, `services/api/tests/test_public_intake_submit.py:54-62`).

## Current supported paths

- Normal member creation goes through `POST /api/v1/members`, whose endpoint accepts `MemberCreate`, calls `create_or_get_member()`, returns `MemberRead`, and uses ETags from the mutation result or existing version (`services/api/app/api/v1/endpoints/members.py:89-109`). `create_or_get_member()` is idempotent by `discord_user_id`: it returns an existing row if found, otherwise creates a member aggregate and inserts a row through `_insert_member()` (`services/api/app/services/members.py:116-177`).
- Exact member reads by Discord id and by UUID are supported and intentionally unfiltered; both return `MemberRead` and expose synthetic rows to authorized callers today (`services/api/app/api/v1/endpoints/members.py:112-145`; `proposals/05-synthetic-member-guard.md:48`, `proposals/05-synthetic-member-guard.md:234`).
- Public application intake is a supported unauthenticated/public route. `POST /api/v1/public/applications` authorizes the public action, calls `submit_public_application()`, and returns only a receipt with `application_id` (`services/api/app/api/v1/endpoints/applications/public.py:18-38`). INIT-120 intentionally creates a synthetic placeholder `members` row whose UUID satisfies `applications.applicant_id` and whose audit actor remains `service/public-intake` rather than the member itself (`proposals/02-public-application-intake.md:65-72`, `proposals/02-public-application-intake.md:327-365`).
- Public submit remains the one approved synthetic-member write path. The proposal requires `submit_public_application()` and `resolve_or_create_public_intake_member()` to keep creating or reusing synthetic applicants (`proposals/05-synthetic-member-guard.md:33-50`, `proposals/05-synthetic-member-guard.md:227-229`).
- INIT-124 guards already block synthetic member writes into real-member-only surfaces. Guarded paths include authenticated application submit, application ownership, trust signal creation, trust compute/recompute, leadership alias expansion, roster entry creation, and member status mutation (`proposals/05-synthetic-member-guard.md:43-50`, `proposals/05-synthetic-member-guard.md:260-310`).

## Known risky or brittle behavior already present

- The discriminator is a magic string in `discord_user_id`. `is_synthetic_member()` accepts either a raw string or any object with `discord_user_id` and returns true when that value starts with `SYNTHETIC_MEMBER_PREFIX = "public:"` (`services/api/app/services/members.py:46-56`).
- Tests encode the prefix as the identity boundary. The predicate unit test says "identifies only public prefix" and covers raw/object values rather than a typed member kind (`services/api/tests/test_synthetic_member_helper.py:10-54`). The public-intake component tests assert the exact `public:[0-9a-f]{32}` shape and assert real ids do not start with `public:` (`services/api/tests/test_public_intake_synthetic_member.py:37-45`, `services/api/tests/test_public_intake_synthetic_member.py:107-134`).
- The prefix was an INIT-124 assumption, not a durable identity model. INIT-124 explicitly chose no schema migration and no `members.kind`, and its assumption register states that `public:` is stable unless a Discord-origin member row can start with that literal prefix (`proposals/05-synthetic-member-guard.md:53-58`, `proposals/05-synthetic-member-guard.md:250-254`).
- Direct test fixture inserts will fail after a non-null column unless updated. Production has one repository insert helper, but tests insert into `members (id, discord_user_id, joined_at, status)` directly in shared fixtures and several test helpers (`services/api/tests/conftest.py:208-227`; repository search also found direct inserts in `services/api/tests/public_intake_fixtures.py`, `services/api/tests/test_members.py`, `services/api/tests/test_roster.py`, and `services/api/tests/chapter_governance_helpers.py`).
- The RCA says `members.kind` is the correct first slice but is not the full OAuth/linking solution. It removes prefix guards but does not link identities or re-point applications (`.tmp/rca/discord-oauth-linking-FINDINGS.md:140-165`, `.tmp/rca/discord-oauth-linking-FINDINGS.md:229-259`).

## Adjacent surfaces inside the blast radius

- Authenticated application submit: `_submit_application_internal()` rejects a synthetic applicant unless `submission_authority` is `PUBLIC_INTAKE` (`services/api/app/services/applications.py:618-632`). Behavior and error code `applicant_synthetic_not_allowed` should stay the same while the predicate source changes to `member.kind`.
- Application owner/claim/reassign/reactivate: `_require_non_synthetic_application_member()` is used for claim reviewer id, reassign `new_owner_id`, and reactivate owner resolution (`services/api/app/services/applications.py:324-336`, `services/api/app/services/applications.py:867-907`). Behavior and error code `owner_synthetic_not_allowed` should stay unchanged.
- Trust: `create_trust_signal()`, `compute_trust()`, and `_recompute_once()` reject synthetic subjects before inserting signals, upserting profiles, or recomputing from active signals (`services/api/app/services/trust.py:291-321`, `services/api/app/services/trust.py:384-397`, `services/api/app/services/trust.py:474-486`). Current implementation returns `trust_subject_synthetic_not_allowed`; the proposal text also references `trust_member_synthetic_not_allowed`, so tests and API expectations should use the code already shipped unless Phase 3 deliberately renames it.
- Roster: `_validate_roster_member()` stops UUID-backed synthetic members from entering roster entries before `_insert_roster_entry()` (`services/api/app/services/roster.py:120-158`). Non-UUID `member_id` strings still pass through as before.
- Leadership / authority read models: `_resolve_member_aliases()` supports `allow`, `omit`, and `reject`; direct leadership context rejects synthetic aliases and succession-plan aggregation omits them (`services/api/app/services/authority.py:145-201`, `services/api/app/services/read_models.py:247-252`, `services/api/app/services/authority.py:549-553`).
- Member status mutation: `patch_member_status()` fetches and locks the row, rejects synthetic members, then validates and writes the status transition (`services/api/app/services/members.py:229-295`).
- Public-intake member creator: `resolve_or_create_public_intake_member()` is in the blast radius because it must create rows with `kind='public_intake'`, while `create_or_get_member()` must create normal API rows with `kind='discord'` (`services/api/app/services/members.py:116-206`).
- Audit substrate: no audit schema change is needed. Current member creation/state mutation flows use `mutate_entity()` with request/action payloads and projection state changes, and INIT-124 already treats synthetic members as application subjects while the actor is `service/public-intake` (`services/api/app/services/members.py:138-166`, `proposals/05-synthetic-member-guard.md:227-228`). If `kind` is exposed in `MemberRead` but not accepted from `MemberCreate`, it can remain a projection discriminator rather than a new caller-controlled audit field.

## Adjacent public or user-reachable paths

- `POST /api/v1/public/applications` must remain behaviorally unchanged: accepted public submissions should still create/reuse a public-intake member, create an application, route it to queued state, and return a receipt (`services/api/app/api/v1/endpoints/applications/public.py:18-38`, `services/api/app/services/applications.py:773-805`). Existing tests assert queued application state, route review actor `public-intake`, and `applicant_discord_user_id` with the public prefix (`services/api/tests/test_public_intake_submit.py:54-70`).
- `POST /api/v1/applications` authenticated submit must still reject public-intake applicants with stable HTTP 422 semantics and no application insert. The only intended internal exception is `_SubmissionAuthority.PUBLIC_INTAKE` (`services/api/app/services/applications.py:618-632`, `proposals/05-synthetic-member-guard.md:260-268`).
- Officer and operational routes must keep rejecting synthetic/public-intake member ids at the same boundaries: application owner transitions, trust signal/compute/recompute, leadership context, roster create, and member status PATCH (`proposals/05-synthetic-member-guard.md:270-310`).
- Exact member reads remain user-reachable to authorized callers and should now expose the discriminator if `MemberRead.kind` is added. This is probably acceptable because `kind` is not sensitive and makes the identity contract explicit; it also prevents clients from relying on the `discord_user_id` prefix (`services/api/app/api/v1/endpoints/members.py:112-150`, `services/api/app/contracts/members.py:25-32`).
- No Discord-visible mutation is part of this slice. INIT-124 also recorded that no Discord-visible mutation occurs for the guard-only surface (`proposals/05-synthetic-member-guard.md:231-236`), and INIT-125A is likewise local schema/API behavior plus tests.

## Deployment mode and cohort

- Deployment should be local first, with the same Alembic migration applying to every channel. BL-008 is already decomposed and INIT-125A is specifically the `members.kind` schema column plus guard migration (`plans/BACKLOG.md:223-245`).
- Migration pattern should follow existing Alembic backfill practice for adding non-null columns to populated tables: add nullable, backfill with SQL, alter to non-null, then add check constraints. `wu-028a_permission_drift_widening.py` uses that pattern for `permission_drift.kind` (`migrations/versions/wu-028a_permission_drift_widening.py:34-53`, `migrations/versions/wu-028a_permission_drift_widening.py:83-110`). `wu-003b_audit_context_columns.py` shows the alternate server-default bridge pattern for a non-null add, followed by dropping the default (`migrations/versions/wu-003b_audit_context_columns.py:17-38`).
- The locked sub-slice excludes Discord OAuth, conversion, historical roster cleanup, and `linked_pending`. Later backlog items own Authentik/Discord OAuth, conversion/application re-pointing, and historical cleanup/read hardening (`plans/BACKLOG.md:236-245`, `plans/BACKLOG.md:344-380`).

## Open questions for proposal

- Exact migration mechanics: prefer add `kind` nullable, backfill, alter `nullable=False`, create `members_kind_valid`, with no lasting `server_default`; or add `nullable=False` with a temporary default and then drop it. Existing migrations show both patterns, but the backfill pattern maps better to prefix-derived values (`migrations/versions/wu-028a_permission_drift_widening.py:34-110`, `migrations/versions/wu-003b_audit_context_columns.py:17-38`).
- Migration placement/head: the RCA sketch says "likely `migrations/versions/wu-043_members_kind.py`" and cites a then-current single head (`.tmp/rca/discord-oauth-linking-FINDINGS.md:234-239`). The proposal should verify the current Alembic head before naming the new migration.
- Normal member creation path: repository search found one production `INSERT INTO members`, `_insert_member()`, reached by `create_or_get_member()`; public intake also reaches that same path through `resolve_or_create_public_intake_member()` (`services/api/app/repositories/members.py:58-79`, `services/api/app/services/members.py:116-206`). The proposal should decide whether to pass an internal `kind` argument through `create_or_get_member()` or branch inside the public-intake helper without allowing external clients to choose `kind`.
- Read contract: should `kind` be exposed in `MemberRead`? Probably yes: it is not sensitive, exact member reads are already allowed, and exposing it discourages prefix parsing by clients (`services/api/app/contracts/members.py:25-32`, `services/api/app/api/v1/endpoints/members.py:112-150`).
- Helper contract: should `is_synthetic_member()` accept only member-like rows/objects with `kind`, or still accept strings? Locked direction says prefix-check removal, so keeping raw-string support would be a compatibility shim. The proposal should narrow the helper to row/object input and update call sites to pass fetched rows rather than `discord_user_id` strings.
- Test fixture strategy: direct test inserts need `kind` values. Shared fixtures should make real members `kind='discord'` and public-intake fixtures `kind='public_intake'`; tests that currently prove prefix behavior should be rewritten to prove kind behavior and that a `discord_user_id` prefix alone is not the discriminator.
- Error-code consistency: implementation currently emits `trust_subject_synthetic_not_allowed`, while INIT-124 prose mentions `trust_member_synthetic_not_allowed` in some places (`services/api/app/services/trust.py:112-119`, `proposals/05-synthetic-member-guard.md:246`, `proposals/05-synthetic-member-guard.md:278-286`). INIT-125A should preserve the shipped behavior unless Phase 3 explicitly scopes an API error rename.
