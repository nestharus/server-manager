The current local Kustomization includes `alembic-migration-job.yaml`, API resources, public-intake rate limit, Discord deployment, object-storage Job, and network policies, but no form seed resource (`gitops/channels/local/applications/server-manager/kustomization.yaml:3-21`).
- `gitops/channels/local/applications/server-manager/alembic-migration-job.yaml`: ordering dependency. The existing migration Job runs `alembic -c /app/alembic.ini upgrade heads` using the API image and `DATABASE_URL` secret (`gitops/channels/local/applications/server-manager/alembic-migration-job.yaml:1-45`). The seed must not run before `form_definitions`, `activity_actions`, `activity_state_changes`, and `aggregate_heads` exist.
- New seed content surface under `gitops/channels/local/applications/server-manager/`: either a standalone form-content YAML such as `seed-public-intake-form.yaml`, or inline data in a Job/ConfigMap. Canonical content is locked to two fields: `character_name` short required label `Character name`, and `application_text` long required label `Application text`; this matches the INIT-118 web contract (`infra/tests/fixtures/web-ui/contract.json:36-78`) and the current public-intake test fixture (`services/api/tests/public_intake_fixtures.py:53-75`).
- `migrations/versions/wu-021_forms.py`: the seed writes into the existing `form_definitions` table. The table requires scope/version/name/target/JSON field and routing data plus publisher fields (`migrations/versions/wu-021_forms.py:17-42`), enforces global scope as `scope_kind='global' AND scope_id IS NULL` (`migrations/versions/wu-021_forms.py:43-69`), and has uniqueness on `(scope_kind, scope_id, version)` plus one current row per scope using `NULLS NOT DISTINCT` (`migrations/versions/wu-021_forms.py:72-89`).
- `services/api/app/contracts/applications.py`: no contract change expected, but the seed data must satisfy `ApplicationScope`, `ApplicationFormField`, `FormDefinitionPublish`, and `FormDefinitionRead`. Global scope forbids `scope_id` (`services/api/app/contracts/applications.py:62-77`), field ids and labels are validated (`services/api/app/contracts/applications.py:80-140`), publish bodies require unique field ids (`services/api/app/contracts/applications.py:155-181`), and not-found errors include the current-form scope string (`services/api/app/contracts/applications.py:375-385`).

- The day-1 web payload is global scope with `responses.character_name` and `responses.application_text` because the public web fixture has no chapter selector (`proposals/02-public-application-intake.md:166-184`; `infra/tests/fixtures/web-ui/contract.json:36-78`).
- Public submit currently works in component tests only after `seed_global_public_application_form()` inserts a current global `form_definitions` row directly (`services/api/tests/public_intake_fixtures.py:53-99`; `services/api/tests/test_public_intake_submit.py:36-55`; `services/api/tests/test_public_application_route.py:43-69`).
- Fresh local bringup currently does not create that row. BL-002 records that fresh `humility-local` fails until manual SQL inserts a current global form (`plans/BACKLOG.md:60-76`), and INIT-120 residual R4 records the same missing seed and two-field workaround (`.tmp/init-120/phase6/STEP6C_DONE.md:127-135`).
- Authenticated form authoring is supported through `POST /api/v1/application-forms`: tests grant `application_form.publish`, call the endpoint with `If-Match`, verify versions and ETags, then `GET /current` returns the latest form (`services/api/tests/test_forms.py:36-47`, `services/api/tests/test_forms.py:88-129`). - Authenticated application submit is supported through `POST /api/v1/applications`: callers provide actor headers, an applicant id, scope, responses, and client id (`services/api/app/api/v1/endpoints/applications/lifecycle.py:45-57`; `services/api/tests/test_applications.py:121-157`). Test setup publishes a chapter-scoped form first through the form API (`services/api/tests/test_applications.py:136-149`).
- Discord submission is already converged on the authenticated application API: it resolves a Discord user to a member, posts to `/api/v1/applications`, passes user actor headers, and sends the command scope through unchanged (`services/discord/app/handlers/application_submission.py:47-93`). It is adjacent but not directly repaired by a global seed because its command can target chapter scope.

## Known risky or brittle behavior already present

- Fresh local deployment has no durable form bootstrap. The RCA traces the current failure: public submit accepts the global payload, converts it to the existing submit lifecycle, then `_submit_application_internal()` raises `FormDefinitionNotFoundError` when no current global form exists, which the endpoint maps to 404 `application_not_found` (`.tmp/rca/public-intake-form-seed-FINDINGS.md:56`; `services/api/app/services/applications.py:598-604`; `services/api/app/api/v1/endpoints/applications/_shared.py:63-68`).
- Plain Kustomize resource inclusion is not a completion-order guarantee. The local Kustomization lists the Alembic Job and API deployment as sibling resources (`gitops/channels/local/applications/server-manager/kustomization.yaml:3-21`), while the Alembic Job itself has only Kubernetes retry semantics (`gitops/channels/local/applications/server-manager/alembic-migration-job.yaml:10-20`). A seed Job that requires migrated tables needs its own readiness/wait behavior or another explicit ordering mechanism.
- Direct SQL that inserts only `form_definitions` can create split-brain behavior. `_get_current_form_for_submit()` first tries the repository lookup, then falls back to a raw query against `form_definitions` (`services/api/app/services/applications.py:447-485`), so public submit can work from a projection-only SQL seed. The canonical `get_current_form_for_scope()` path joins to `aggregate_heads` (`services/api/app/repositories/forms.py:10-30`, `services/api/app/repositories/forms.py:91-106`), so `GET /api/v1/application-forms/current?scope_kind=global` can still fail if the `application_form|global|` head is missing.
- The aggregate/audit substrate is part of form authoring semantics. `mutate_entity()` creates or locks aggregate heads, inserts accepted/rejected/failed `activity_actions`, inserts `activity_state_changes`, and advances heads (`services/api/app/services/mutations.py:94-185`, `services/api/app/services/mutations.py:191-225`; `migrations/versions/wu-002_activity_substrate.py:18-135`). SQL seeding can be made consistent, but it must deliberately seed or preserve this state rather than bypass it accidentally.
- Current-row and version uniqueness make rerun semantics important. `ux_form_definitions__current_per_scope` permits only one current row per `(scope_kind, scope_id)` with global `NULL` treated as equal (`migrations/versions/wu-021_forms.py:78-83`), and `ux_form_definitions__scope_version` prevents duplicate version numbers for the same scope (`migrations/versions/wu-021_forms.py:72-77`). Concurrent seed runs, seed-vs-officer publication, or blind "archive then insert version 1" behavior can hit conflicts or replace operator state.
- Existing test fixture SQL is not production-safe as-is. It archives any current global form and inserts version 1 with `published_by_kind='service'`, `published_by_id='public-intake'`, but does not create an aggregate head or audit action (`services/api/tests/public_intake_fixtures.py:76-99`). That is acceptable fixture setup for service tests, not a complete local runtime bootstrap.
- API-vs-direct-SQL has a real authority/audit tradeoff. The endpoint uses actor headers captured by middleware (`services/api/app/core/actor.py:26-81`) and DB authority grants evaluated by `RequireAuthority`, not Cedar public-intake policy (`services/api/app/core/dependencies.py:56-87`, `services/api/app/core/dependencies.py:129-138`). The permission string in code is `application_form.publish` (`services/api/app/api/v1/endpoints/applications/forms.py:19-24`), while Cedar public-intake policies only cover `application:submit_public` and service identities do not include `public-intake` (`policy/cedar/channels/local/services/server-manager-api/policies.json:10-17`; `policy/cedar/channels/local/services/server-manager-api/service-identities.json:1-20`; `infra/tests/test_public_intake_policy_fixture.py:86-99`).
- Migration-seeded service grants exist elsewhere, but those are non-reversible operational rows. Read-model and SLA migrations seed service grants idempotently and intentionally avoid removing them on downgrade (`migrations/versions/wu-031_read_models.py:41-92`; `migrations/versions/wu-037_ticket_sla_triggers.py:96-140`). That pattern is evidence for idempotent operational seeding, but it also highlights rollback/state ownership risk if a form seed is tied to Alembic migration lifecycle.

## Adjacent surfaces inside the blast radius

- INIT-120 public submit path: the seed should make `/api/v1/public/applications` operational on fresh local bringup. It must preserve the INIT-120 audit semantics: public submit and route actions are stamped as service actor `public-intake` on `api:/api/v1/public/applications` (`proposals/02-public-application-intake.md:300-325`; `services/api/app/services/applications.py:151-155`, `services/api/app/services/applications.py:762-769`).
- Web `/applications` contract: the visible public form and submit payload are the two-field global contract in `infra/tests/fixtures/web-ui/contract.json` (`infra/tests/fixtures/web-ui/contract.json:36-78`). The seed should align DB runtime state with that contract, not introduce a richer form or chapter selector in this slice.
- Discord submission service: Discord posts `ApplicationSubmission` to `/api/v1/applications` with command-provided scope and user actor headers (`services/discord/app/handlers/application_submission.py:58-76`). A global seed should not disturb chapter-scoped form lookup or Discord command behavior.
- Authenticated `POST /api/v1/applications`: authenticated users also use `_submit_application_internal()` and current-form lookup (`services/api/app/services/applications.py:723-734`, `services/api/app/services/applications.py:572-604`). Adding a global current form could make global-scope authenticated submissions possible for actors with `application.submit` at global scope; that should be treated as adjacent existing capability, not a new public route.
- `form_definitions` uniqueness: one current form per scope and one version per scope are enforced at the database layer (`migrations/versions/wu-021_forms.py:72-83`). The implementation proposal must define exactly how the seed behaves when a current global form already exists.
- Audit and optimistic-locking substrate for form authoring: API publication uses `application_form|global|` aggregate id, expected version, activity actions, state changes, and ETags (`services/api/app/services/forms.py:36-38`, `services/api/app/services/forms.py:78-166`; `services/api/tests/test_forms.py:88-129`). Direct SQL must either preserve those invariants or document why the seed is outside authoring semantics.
- Authority substrate if API publication is selected: `application_form.publish` is granted and evaluated through `authority_grants`, where permissions are stored as JSON and active grants are scope/permission matched (`migrations/versions/wu-004_authority_foundation.py:18-74`; `services/api/app/services/authority.py:182-267`, `services/api/app/services/authority.py:334-382`).

## Open questions for proposal

- Should the seed be coupled to Alembic migration lifecycle or tracked as a separate one-shot Job? Locked direction says local GitOps Job after Alembic, but the proposal still must decide whether this Job is effectively migration-coupled operational state or an independently rerunnable bootstrap. This matters because existing migration seed patterns intentionally avoid rollback deletion for live operational grants (`migrations/versions/wu-031_read_models.py:89-92`; `migrations/versions/wu-037_ticket_sla_triggers.py:136-140`).
- Should the Job publish through the API/service path or do direct SQL? API/service publication preserves archive, aggregate head, activity action, state change, ETag, and current-form lookup semantics (`services/api/app/services/forms.py:78-166`), but it requires actor headers and an active DB authority grant for `application_form.publish` (`services/api/app/api/v1/endpoints/applications/forms.py:19-24`; `services/api/app/core/dependencies.py:56-87`). Direct SQL is simpler but must seed both `form_definitions` and `application_form|global|` aggregate consistency, or the canonical current-form API remains inconsistent (`services/api/app/repositories/forms.py:10-30`, `services/api/app/repositories/forms.py:91-106`). NEEDS_RESEARCH: the prompt mentions a Cedar grant for `application.publish_form`, but the current FastAPI authority permission is `application_form.publish`, and Cedar public-intake policy is unrelated to this endpoint.
- Should canonical form content live in a repo YAML consumed by the Job or inline in a ConfigMap/Job script? The content itself is locked to the two-field INIT-120 shape, but source-of-truth mechanics remain a proposal choice. YAML is easier to diff and reuse across tests; inline ConfigMap data keeps the local bootstrap self-contained. Either way, runtime source of truth remains Postgres, not web fixture JSON or legacy form YAML (`.tmp/rca/public-intake-form-seed-FINDINGS.md:72`, `.tmp/rca/public-intake-form-seed-FINDINGS.md:88`).
- What exactly is idempotent behavior when a current global form already exists? RCA recommends avoiding duplicate current rows and avoiding blind overwrite of an officer-published current form unless the proposal explicitly scopes replacement (`.tmp/rca/public-intake-form-seed-FINDINGS.md:82`, `.tmp/rca/public-intake-form-seed-FINDINGS.md:102`). The proposal needs a precise rule for "seed already present", "different current global form present", and "aggregate head missing for existing projection".
