## Current supported paths

- Authenticated API submission works today through `POST /api/v1/applications` when the caller supplies actor headers and a body shaped as `ApplicationSubmission`. The tests create an applicant member, publish a form, send `applicant_id`, `scope`, `responses`, and `client_application_id`, and assert `201`, `state == "queued"`, ETag `"2"`, and one route review row in `services/api/tests/test_applications.py:121-193`.
- Authenticated reviewers use sibling application routes after submission. `services/api/app/api/v1/endpoints/applications/lifecycle.py:44-81` supports `GET /api/v1/applications/{id}` and `POST /api/v1/applications/{id}/transitions` with actor dependency and ETag parsing; reviewer tests cover claim and owner-only review/decision behavior in `services/api/tests/test_applications.py:270-418`.
- Public web shell and form route exist without auth at `web.local.humility.local`. The fixture defines the public host and `/applications` route in `infra/tests/fixtures/web-ui/contract.json:4-18`, Pomerium permits public unauthenticated access to non-`/admin` web paths in `gitops/channels/local/auth/pomerium/secrets-infisicalsecret.yaml:48-57`, and the SPA renders public/form/admin routes in `services/web/src/main.tsx:14-31` and `services/web/src/main.tsx:108-154`.
- Web-driven submit is currently fixture-backed in tests and auth-blocked against the real API. The SPA posts `character_name` and `application_text` to `/api/applications` in `services/web/src/main.tsx:124-138`; the component test fulfills the route with `201` itself in `services/web/tests/compat.spec.ts:70-86`; the real nginx proxy forwards that request to `/api/v1/applications` in `containers/server-manager/nginx-web.conf:8-20`; that endpoint then asks `get_current_actor` for actor context in `services/api/app/api/v1/endpoints/applications/lifecycle.py:29-35`, producing `401 actor_identity_missing` when no actor headers exist via `services/api/app/core/dependencies.py:45-53`.
- The original Discord-first applicant flow is planned, but not present as one complete current source path. `proposals/18-applications.md:14-24` describes `/apply`, answer collection, SQLite persistence, queue message, private thread, and review view; `proposals/18-applications.md:237-269` shows the intended end-to-end flow. Current legacy code registers `/apply`, checks chapter/blacklist/duplicate state, and opens the first modal in `daemon/applications.py:387-455`, but `ApplicationModal.on_submit` only records answers in memory and replies `"Your application draft was recorded"` in `daemon/applications.py:184-211`; it does not call `db.create_submission`, post the queue message, create a thread, or update refs.
- The newer Discord service has a supported API submission adapter, not the same `/apply` modal flow. `services/discord/app/handlers/application_submission.py:47-93` resolves the Discord user to a member, posts to `/api/v1/applications` with `applicant_id`, `scope`, `responses`, `client_application_id`, and user actor headers, then returns a success or duplicate message. `services/discord/tests/test_application_submission.py:66-91` pins that request shape.
- Discord interview/review side effects are separate from initial submission. Interview handling can create or reuse an interview thread in `services/discord/app/handlers/application_interview.py:90-157` and then POST `/api/v1/applications/{id}/interview` in `services/discord/app/handlers/application_interview.py:197-210`. Review handlers POST application transitions and optionally send an outcome to the review channel in `services/discord/app/handlers/application_review.py:51-99`.

## Known risky or brittle behavior already present

- Missing actor context is an explicit 401 contract. `services/api/app/core/dependencies.py:45-53` raises `actor_identity_missing` when no actor is in context; `services/api/app/core/actor.py:63-81` lets anonymous requests through middleware when actor headers are absent, so endpoint-level `Depends(get_current_actor)` is where the lifecycle route fails.
- Public web payload shape does not match the API contract. The SPA submits `character_name` and `application_text` in `services/web/src/main.tsx:9-12` and `services/web/src/main.tsx:124-135`; the API requires `applicant_id`, `scope`, and `responses` in `services/api/app/contracts/applications.py:200-204`.
- Even with syntactically valid application data, anonymous submit does not satisfy domain authority. `services/api/app/services/applications.py:244-260` allows submit only when the actor is the applicant user or has a grant for `application.submit`.
- The current application persistence model requires a real member identity. `services/api/app/services/applications.py:488-490` rejects submissions whose `applicant_id` does not exist as a member, and `migrations/versions/wu-022_applications.py:51-56` enforces `applications.applicant_id -> members.id`.
- The form lookup model requires an existing current form for the submitted scope. `services/api/app/services/applications.py:492-499` calls `get_current_form_for_scope` and raises when none exists.
- The R.22/R.26 web submit tests do not prove a live backend contract. `services/web/tests/compat.spec.ts:70-86` and `infra/tests/e2e/lib/playwright/browser-flow.mjs:42-63` both intercept and fulfill `/api/applications`; the RCA records that the route/status/body contract exists only in the web fixture and fixture-backed tests in `.tmp/rca/public-application-intake-FINDINGS.md:27-33`.
- No anonymous Cedar policy or anonymous service-account-JWT pattern exists in the current access bundle. The access matrix contains only named user/service principals in `infra/tests/fixtures/contracts/access_policy_matrix.yml:1-37`; the policy bundle mirrors named principals in `policy/cedar/channels/local/services/server-manager-api/policies.json:1-26`; service identities are only Buildkite and Crossplane in `policy/cedar/channels/local/services/server-manager-api/service-identities.json:1-20`.
- Pomerium currently separates public web from protected admin/protected API by host/path, not by a named public form-intake API route. `gitops/channels/local/auth/pomerium/secrets-infisicalsecret.yaml:47-62` makes `web.local.humility.local` broadly public except `/admin`, while `protected-api.local.humility.local` is authenticated; the direct `api.local.humility.local` ingress in `gitops/channels/local/applications/server-manager/api-ingress.yaml:1-30` is not Pomerium-protected.
- The current Discord application story is split. Legacy `/apply` uses SQLite draft/session concepts in `daemon/applications.py:28-36` and `daemon/db.py:29-44`, while the current service adapter writes Postgres `applications` through the API in `services/discord/app/handlers/application_submission.py:61-76`. This split means web intake cannot assume there is one canonical Discord implementation to converge with.
- The current API `applications` state machine depends on multiple migrations. The contract includes `interview` and `waitlisted` in `services/api/app/contracts/applications.py:36-45`, while the original applications migration only permits `submitted`, `queued`, `claimed`, `in_review`, `approved`, `denied`, and `withdrawn` in `migrations/versions/wu-022_applications.py:70-72`; later interview/waitlist support widens the check and adds `interview_thread_id` in `migrations/versions/wu-035_application_interview.py:33-60`, so submit behavior changes need to account for the full migration chain.
- There is no visible Kong rate-limit plugin attached to this path. Search found Kong CRDs and ingress resources but no application `KongPlugin` or `konghq.com/plugins` binding for `api.local.humility.local`, `web.local.humility.local`, or `/api/applications`; `gitops/channels/local/applications/server-manager/api-ingress.yaml:9-12` has only cert-manager annotations.

## Adjacent surfaces inside the blast radius

- `applications` schema and FKs: the real table requires `applicant_id`, `form_definition_id`, `form_version`, immutable form snapshot, target scope, JSON responses, and state timestamps in `migrations/versions/wu-022_applications.py:19-96`. Any public intake path has to decide whether it creates this real row and, if so, what member-backed `applicant_id`, scope, form, and responses it uses.
- Member/trust identity: `members.id` is keyed to `discord_user_id` in `migrations/versions/wu-011_members.py:17-43`; `trust_profiles.member_id` depends on members in `migrations/versions/wu-012_trust.py:17-54`. Anonymous intake has no existing member/trust subject unless the proposal defines one.
- Form model: current production code calls the table `form_definitions`, not `application_forms` / `application_form_versions`. `migrations/versions/wu-021_forms.py:17-90` stores current form definitions by scope/version, and `services/api/app/services/applications.py:517-528` snapshots those fields into application rows.
- Audit chain: `mutate_entity` records accepted/rejected/failed actions with non-null `actor_kind`, `actor_id`, correlation, request surface, request payload, and status in `services/api/app/services/mutations.py:72-185` and failure actions in `services/api/app/services/mutations.py:203-225`. Anonymous submit needs an actor/audit posture before it can use this substrate cleanly.
- Application review ledger: submission routing inserts an `application_reviews` row during `_transition_application_locked`, including `actor_kind` and `actor_id`, in `services/api/app/services/applications.py:715-730`; the migration makes those non-null in `migrations/versions/wu-022_applications.py:120-165`.
- Discord flow convergence: legacy `/apply` checks duplicate active SQLite submissions before opening a modal in `daemon/applications.py:409-422`; current API submission uses Postgres duplicate protection by `applicant_id` and `client_application_id` in `services/api/app/services/applications.py:500-507` and `migrations/versions/wu-022_applications.py:112-118`. If public web intake also writes applications, duplicate semantics across Discord/web need a single identity key.
- Discord review/interview side effects: initial API submission only creates a queued application row; interview thread creation is a later Discord handler path in `services/discord/app/handlers/application_interview.py:90-157`. A public web path that claims "Application received" does not currently imply a Discord queue message or thread.
- Cedar policy and tests: access-policy validation expects the repo policy and GitOps ConfigMap to match exactly in `infra/tests/validate_access_policy_local.sh:100-120` and proves only sample user allow/deny at runtime in `infra/tests/validate_access_policy_local.sh:160-202`. Adding an unauthenticated or service-principal submit path changes the matrix.
- Tenant isolation tests: `infra/tests/validate_tenant_isolation_local.sh:164-207` validates Cedar tenant policy and waits for the Cedar bootstrap job. A public cross-host API path may need explicit treatment so tenant/channel access assumptions do not silently broaden.
- Web network policy: the web pod now has egress to the API service in `gitops/channels/local/applications/web/networkpolicy.yaml:27-46`; public browser traffic to `/api/applications` therefore reaches the API through the web pod if Pomerium admits the web request.
- Abuse surface: public unauthenticated POST on `web.local.humility.local` would be reachable through a route currently marked public in `gitops/channels/local/auth/pomerium/secrets-infisicalsecret.yaml:54-57`; no rate-limit/resource policy is attached at the visible ingress path today.

## Deployment mode and cohort

- Current live proof target is the local channel. `infra/channels/local.yaml:1-24` defines `id: local`, k3d/k3s target, GitOps path `./gitops/channels/local`, and Flux kustomization `humility-local`. Local is a real deployment target, not a dry run, per `infra/README.md:14-19`.
- Remote channel configuration exists, but remote apply is plan-only in current docs. `infra/channels/dev.yaml:1-24` defines the `dev` channel as Vultr VM k3s; `docs/deployment-substrate.md:23-55` lists active `local` and `dev` channel declarations and says INIT-101 validates remote plan shape without real Vultr apply.
- The environment model is channel-based: local and remote use the same component shape with different provider and endpoint config. `docs/deployment-substrate.md:13-21` states the channel template model and per-channel provider/endpoint details; `infra/README.md:458-476` describes durable channel declarations and ephemeral children.
- For this surface, local hostnames are `web.local.humility.local`, `protected-api.local.humility.local`, and `api.local.humility.local`; remote equivalents are not currently materialized under `gitops/channels/dev`, so a proposal needs the same code path with channel-specific provider/endpoint config rather than a local-only route exception.

## Open questions for proposal

- What `applicant_id` does anonymous web intake carry? Current evidence: `ApplicationSubmission` requires `applicant_id` (`services/api/app/contracts/applications.py:200-204`), the service checks that member exists (`services/api/app/services/applications.py:488-490`), and the DB FK requires `members.id` (`migrations/versions/wu-022_applications.py:51-56`). Resolving evidence would be a product/security decision naming synthetic member, OAuth-pending member, or separate pending table semantics.
- Is the web form a fallback replacement surface or an equal first-class intake path? Current evidence: `proposals/01-v1-scope.rev1.md:500-504` says richer web forms are a fallback replacement if Discord components cannot support required inputs, while the R.22 fixture already exposes `/applications` as public form submit (`infra/tests/fixtures/web-ui/contract.json:36-58`).
- Should public web intake create real `applications` rows immediately? Current evidence: the existing API route creates real rows and routes to `queued` in `services/api/app/services/applications.py:479-613`, but current web tests only assert a generic message and do not assert an application id, version, ETag, queue state, or Discord side effect (`services/web/tests/compat.spec.ts:70-96`).
- If the public submit path stays unauthenticated at Pomerium, what API-level identity and authorization mechanism should it use? Current evidence: no anonymous Cedar or service identity entry exists in `infra/tests/fixtures/contracts/access_policy_matrix.yml:1-37`, `policy/cedar/channels/local/services/server-manager-api/policies.json:1-26`, or `policy/cedar/channels/local/services/server-manager-api/service-identities.json:1-20`.
- Does unauthenticated submission produce audit records, and what actor satisfies the audit requirement? Current evidence: activity actions require actor fields (`migrations/versions/wu-002_activity_substrate.py:17-49`), and `mutate_entity` records actor context for application submit (`services/api/app/services/mutations.py:123-185`).
- What rate-limit or abuse control is required on day 1? Current evidence: public web paths are admitted by Pomerium (`gitops/channels/local/auth/pomerium/secrets-infisicalsecret.yaml:54-57`), web-to-API egress is allowed (`gitops/channels/local/applications/web/networkpolicy.yaml:27-46`), and no app-specific Kong rate-limiting plugin is attached to the ingress (`gitops/channels/local/applications/server-manager/api-ingress.yaml:9-12`).
- Which Discord flow is canonical for convergence? Current evidence: legacy `/apply` is incomplete and SQLite-backed (`daemon/applications.py:184-211`, `daemon/db.py:29-44`), while the current Discord service writes Postgres applications through the API (`services/discord/app/handlers/application_submission.py:61-76`). The proposal needs to resolve whether public web converges with the API-backed Discord service or with the older `/apply` design.
- What should the public success response expose? Current evidence: web fixture expects only `{"message": "Application received"}` (`infra/tests/fixtures/web-ui/contract.json:52-58`), while authenticated API submission returns full `ApplicationRead` with ETag (`services/api/app/api/v1/endpoints/applications/lifecycle.py:29-41` and `services/api/tests/test_applications.py:178-185`).
- How should local and remote channel configs represent the public intake route? Current evidence: local Pomerium hardcodes `web.local.humility.local` and `protected-api.local.humility.local` in `gitops/channels/local/auth/pomerium/secrets-infisicalsecret.yaml:47-62`, while the channel model expects provider/endpoint differences to live in channel config (`docs/deployment-substrate.md:13-21`).
