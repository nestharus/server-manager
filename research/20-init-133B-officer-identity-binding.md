# INIT-133B officer identity binding research

## TL;DR

Recommend **M1, with the existing member resolver as the final step**: make the Pomerium officer login carry a verifiable Authentik `discord_user_id` claim, forward it as `x-pomerium-claim-discord-user-id`, and have the web-officer bridge derive `ActorIdentity(actor_kind="user", actor_id=<member uuid>)` only from that Pomerium-asserted Discord snowflake. This fixes A1 without adding a new database identity-link subsystem, keeps `ActorIdentity` and application ownership semantics intact, and aligns with the BL-019D-beta decomposition already recorded in the backlog: applicant receipts remain applicant-only, while officer actor identity comes from the Pomerium/Authentik chain (`plans/BACKLOG.md:556-564`).

## Evidence

### Current state

#### Repo

- The proposal currently composes Pomerium with the applicant receipt: `/api/v1/me` supplies a Pomerium principal, but the proposed bridge verifies `applicant_receipt`, resolves that receipt's Discord snowflake to a member UUID, then constructs `ActorIdentity(actor_kind="user", actor_id=<member uuid>)` (`proposals/13-init-133B-i-officer-queue.md:13-16`, `proposals/13-init-133B-i-officer-queue.md:206-214`).
- The audit gate rejected that exact composition: the `applicant_receipt` cookie is set by `/auth/discord/callback` with `Path=/`, so an officer can hold a Pomerium session for subject X and a Discord receipt for user Y; the bridge would authorize and audit as Y (`plans/risk/init-133B-i-audit.md:7-15`).
- `/api/v1/me` currently trusts only Pomerium headers for `subject`, `email`, and `name`; it does not parse `groups` or any Discord identity claim yet (`services/api/app/api/v1/endpoints/me.py:18-36`, `services/api/app/contracts/web.py:13-18`).
- The existing web-admin endpoint pattern is Pomerium-only: `/api/v1/web/admin/chapters` depends on `get_pomerium_principal` and does not build an application actor (`services/api/app/api/v1/endpoints/web.py:18-23`).
- Applicant OAuth already proves the Authentik pattern needed for a Discord snowflake claim: the blueprint stores `info.get("id")` as `request.user.attributes["discord_user_id"]`, defines a `discord_user_id` scope mapping, includes claims in the ID token, and wires the `server-manager-applicant` application to the Discord source (`gitops/channels/local/auth/authentik/bootstrap-blueprint-configmap.yaml:45-68`, `gitops/channels/local/auth/authentik/bootstrap-blueprint-configmap.yaml:88-114`).
- The Pomerium config points at Authentik's `pomerium` OIDC app and requests only `openid email profile` today; it forwards `email`, `sub`, `groups`, and `name` through `jwt_claims_headers`, but not `discord_user_id` (`gitops/channels/local/auth/pomerium/secrets-infisicalsecret.yaml:32-46`).
- The repo does **not** currently define the Authentik `pomerium` OAuth2 application/provider in the mounted bootstrap blueprint; `render-values.yaml` mounts only `authentik-init-114-blueprint`, whose data defines local sample users and the applicant Discord OAuth app (`gitops/channels/local/auth/authentik/render-values.yaml:13-15`, `gitops/channels/local/auth/authentik/bootstrap-blueprint-configmap.yaml:10-37`, `gitops/channels/local/auth/authentik/bootstrap-blueprint-configmap.yaml:37-114`).

- The callback sets the receipt cookie after validating the applicant OIDC token; cookie scope is `/`, `secure`, `httponly`, `SameSite=Lax`, and no Pomerium principal participates in the callback (`services/api/app/api/v1/endpoints/auth_discord.py:61-85`).
- Members are already keyed by UUID plus unique `discord_user_id`; `kind` distinguishes real Discord rows from `public_intake` synthetic rows (`migrations/versions/wu-011_members.py:17-43`, `migrations/versions/wu-043_members_kind.py:15-31`).

#### External / norms

- Authentik supports the needed OP/RP split: it can act as an OAuth2/OIDC provider for Pomerium and as a relying party/source for Discord login in the same installation ([Authentik OAuth2 provider docs](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/), lines 85-90).
- Authentik OAuth sources can map upstream OAuth claims through source property mappings; the `info` variable contains OAuth claims available to the mapping expression ([Authentik OAuth Source docs](https://docs.goauthentik.io/users-sources/sources/protocols/oauth/), lines 102-124).
- Authentik OAuth2 provider scope mappings add custom claims to access and ID tokens, which matches the existing applicant `discord_user_id` scope mapping pattern ([Authentik provider property mappings docs](https://version-2025-6.goauthentik.io/docs/add-secure-apps/providers/property-mappings/), lines 77-79; [OAuth2 provider docs](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/), lines 181-203).
- Pomerium can request custom IdP scopes with `idp_scopes`; the setting is an OAuth2 scope list and examples show custom configuration, so adding `discord_user_id` is mechanically consistent with the setting ([Pomerium identity provider settings](https://www.pomerium.com/docs/reference/identity-provider-settings), lines 280-316).
- Pomerium can forward arbitrary claims from its session JWT into upstream headers via `jwt_claims_headers`; identity headers are only sent when `pass_identity_headers` is enabled ([Pomerium JWT Claim Headers](https://www.pomerium.com/docs/reference/jwt-claim-headers); [Pomerium pass identity headers per route](https://www.pomerium.com/docs/reference/routes/pass-identity-headers-per-route)).
- Discord's `identify` OAuth2 scope is the minimum normal way to obtain the current user's Discord account identity; Discord documents `identify` as enabling `/users/@me` without email, and `guilds.members.read` only if a guild member object is needed ([Discord OAuth2 docs](https://docs.discord.com/developers/topics/oauth2?sa=D&source=editors&usg=AOvVaw1nL7mE4dLNI_zvQHDnUgCm&ust=1648698859771000), lines 113-147; [Discord User Resource](https://docs.discord.com/developers/resources/user), lines 309-363).
- Discord community-tool dashboards generally bind dashboard access to the logged-in Discord account and Discord permissions, not to a second unbound cookie. MEE6 documents that users log into its dashboard with their Discord account and that administrator roles have dashboard/server-settings access ([MEE6 getting started](https://help.mee6.xyz/support/solutions/articles/101000385394-getting-started-with-mee6)); Apollo's dashboard states it respects Discord permissions ([Apollo dashboard page](https://apollo.fyi/), "Web Dashboard" section).
- General admin tools bind privileged actions to the authenticated team member/session identity: Stripe manages organization/team access by member roles, removes access immediately when a member is removed, and exposes security history by action; GitHub audit log event fields consistently include `actor` and `actor_id` for the initiating authenticated account ([Stripe organization team docs](https://docs.stripe.com/get-started/account/orgs/team), lines 0-17; [GitHub audit events](https://docs.github.com/en/enterprise-server@3.20/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/audit-log-events-for-your-enterprise), lines 1435-1450).

### Mechanism analysis

#### M1 — Authentik/Pomerium `discord_user_id` claim

- **What changes**: Add a Pomerium/officer Authentik blueprint or amend the missing Pomerium app definition so officer login is sourced from Discord or requires a linked Discord source; add a Pomerium OAuth2 scope mapping for `discord_user_id`; add `discord_user_id` to Pomerium `idp_scopes`; add `x-pomerium-claim-discord-user-id: discord_user_id`; parse that header in `me.py` / web-officer bridge; update Authentik/Pomerium static tests.
- **Trust chain**: officer authenticates to Authentik through the configured Discord source; Authentik stores `discord_user_id` from Discord's `identify` result; Authentik includes `discord_user_id` in the Pomerium OIDC token via scope mapping; Pomerium requests that scope and forwards it to the web/API route; bridge validates the header as a Discord snowflake, resolves a `members.kind='discord'` row, constructs `ActorIdentity(actor_kind="user", actor_id=<member uuid>)`, then calls existing application list/transition services.
- **Failure mode if blueprint/table is wrong**: if the source mapping or scope mapping is missing, the header is absent and officer routes must return 401/403 before list/claim. If a user has no linked Discord source, first login cannot use the officer queue. If the Pomerium app remains manually configured outside GitOps, the claim chain is not reproducible and should fail the proposal/risk gate.
- **Diff size estimate**: roughly +30-70 YAML lines for Authentik/Pomerium config, +10-30 Python lines to parse and require the claim, +50-120 test lines. No Alembic migration.
- **Compat with AGENTS.md**: clean single identity chain, no shim, no second actor table, no old behavior fallback. It also follows the backlog's decomposed target that the applicant receipt remains scoped to applicant routes only (`plans/BACKLOG.md:556-564`).
- **Compat with existing tests**: extends `infra/tests/test_applicant_discord_blueprint.py` or adds a sibling Pomerium blueprint test; extends `infra/tests/test_applicant_discord_pomerium.py` to assert the claim header mapping. Must also update the already-identified `/me` JSON exactness test if `CurrentPrincipalRead` grows fields (`services/api/tests/test_web_identity.py:21-42`, `plans/risk/init-133B-i-supported-surface.md:1-12`).
- **Operational implications**: officers must authenticate/link the Discord account that should be the audit actor. Offboarding remains two-part: remove Pomerium/Authentik officer access and revoke/expire application authority grants on the member UUID. If an officer changes Discord accounts, a new member UUID appears or is resolved and authority must be re-granted to the new identity.
- **HCI norm alignment**: strongest. The identity of record is the same identity used for the privileged session, matching Discord dashboard norms and general admin audit logs that record the signed-in actor.

#### M2 — Server-side Pomerium-subject to member link

- **What changes**: Add `member_links` or `members.pomerium_subject`, migration, repository/service helpers, tests, and an operational link-management path. The bridge would look up `x-pomerium-claim-sub`, require a linked member UUID, and optionally reject if an applicant receipt is present and disagrees.
- **Trust chain**: Pomerium authenticates subject; API looks up subject in server-side table; table points to a real Discord member UUID; bridge constructs `ActorIdentity(user, member_uuid)`; existing application services enforce authority and write audit.
- **Failure mode if blueprint/table is wrong**: unlinked officers cannot use the queue. Stale links are worse: a Pomerium account linked to the wrong Discord member produces the same wrong audit actor A1 warned about, just from a persistent table rather than a cookie. If receipt disagreement is retained as a guard, the flow still depends on the applicant receipt and can confuse officers.
- **Diff size estimate**: +1 migration, +1 repository module or members changes, +1 service helper, tests and seed/link fixtures: likely +180-300 lines before UI handling. More if a supported link-management endpoint is required.
- **Compat with AGENTS.md**: acceptable only if the link table becomes the single declared identity-binding system. A temporary manual table with no management/offboarding path risks becoming a deferred stub.
- **Compat with existing tests**: must add migration tests and API bridge cases for unlinked, linked, stale/wrong link, and maybe receipt disagreement. It violates the original supported-surface "no schema change" property (`plans/risk/init-133B-i-supported-surface.md:197-217`), so risk gates would need a wider rerun.
- **Operational implications**: supports non-Discord Authentik login, but creates a lifecycle: initial linking, link correction, Discord account changes, Pomerium subject changes, and offboarding. It also gives operators another identity table to audit.
- **HCI norm alignment**: common in enterprise SSO systems, but weaker here because Humility's domain actor is already Discord/member identity and Discord OAuth is already installed.

#### M3 — Officer routes use the Discord OAuth receipt as the only identity

- **What changes**: Reframe officer login so Discord OAuth is the authenticated identity for officer actions; Pomerium becomes a yes/no edge gate or is keyed to Discord identity. The applicant receipt would need new semantics or a separate officer receipt.
- **Trust chain**: officer logs into Discord OAuth; API trusts that one Discord OAuth session/receipt for actor identity; Pomerium only protects the route, or is removed from identity authority.
- **Failure mode if blueprint/table is wrong**: if the existing applicant receipt is reused, the same broad `Path=/` cookie becomes a privileged officer credential and its 10-minute applicant UX semantics drive officer operations. If a separate officer receipt is added, the project has two Discord receipt systems unless the applicant one is deleted/replaced.
- **Diff size estimate**: +150-300 lines if done cleanly, because it needs separate receipt naming, route policy, tests, and UI auth states. More if Pomerium policy must be tied to Discord identity.
- **Compat with AGENTS.md**: risky. Reusing `applicant_receipt` for officer actions is the rejected A1 pattern. Adding `officer_receipt` beside it is easy to turn into a parallel auth system.
- **Compat with existing tests**: likely touches applicant OAuth tests, Pomerium route tests, and web UI auth fixtures. It also regresses the supported-surface claim that applicant Discord OAuth is consumed read-only (`plans/risk/init-133B-i-supported-surface.md:67-88`).
- **Operational implications**: officers authorize Discord again in the app. Expiry/refresh must be solved for officer use instead of the current short applicant receipt. Pomerium group/officer membership can still disagree with Discord authority unless bound somewhere else.
- **HCI norm alignment**: Discord dashboard tools do use Discord login, but they use it as the primary session identity. In this repo, Pomerium is already the protected admin session, so bolting Discord receipts beside it is less clean than making Pomerium's session carry the Discord identity.

#### M4 — `ActorIdentity(actor_kind="officer", actor_id=<Pomerium subject>)`

- **What changes**: Extend `ActorIdentity` literals, application transition/reviewer logic, authority grant semantics, audit queries, possibly application ownership schema or contract semantics, and tests. Authority would be granted to Pomerium subjects rather than member UUIDs.
- **Trust chain**: Pomerium authenticates subject; API records `actor_kind="officer"` with `actor_id=<sub>`; authority grants are keyed to Pomerium subject; claim ownership either cannot use `owner_id` as a member UUID or needs a separate reviewer identity field.
- **Failure mode if blueprint/table is wrong**: a changed Pomerium subject loses access or strands historical audit/ownership records. If the code partially changes, `_reviewer_id` still raises because review actions require `user` actors with UUID ids (`services/api/app/services/applications.py:266-273`).
- **Diff size estimate**: +300-600 lines minimum, likely more, because it crosses contracts, services, migrations/contracts for ownership, authority grants, and audit readers.
- **Compat with AGENTS.md**: poor for this slice. It creates a second authority/actor namespace while the current domain model already treats application owners as real non-synthetic members.
- **Compat with existing tests**: broad rewrite. It breaks the existing "claim ownership must be a real member UUID" invariant in the proposal and service (`proposals/13-init-133B-i-officer-queue.md:212-214`, `services/api/app/services/applications.py:946-955`).
- **Operational implications**: officer actions no longer tie directly to Discord member identity. Offboarding moves to Authentik/Pomerium and authority grants, but Discord-side member/officer reasoning becomes harder.
- **HCI norm alignment**: acceptable for enterprise tools whose whole staff identity is SSO, but misaligned with a Discord-server management system where the meaningful staff identity is a Discord guild member.

### Recommendation

Pick **M1**. It is the smallest mechanism that removes the unbound-cookie failure while preserving the existing application service contract: Authentik/Pomerium proves the officer's Discord account, and the API still records the existing member UUID as `ActorIdentity.actor_id`. M1 is roughly a YAML/header/test change plus a narrow bridge parse, while M2 adds a durable identity-link subsystem, M3 risks turning the applicant receipt into an officer credential, and M4 rewrites actor/authority/ownership semantics across the application domain. The only caveat is important: 133B-i must make the Pomerium Authentik app/config GitOps-declared enough to test. The repo currently proves the applicant app's claim pattern, but not the Pomerium app definition.

### What 133B-i still owes

- **§3 Scope**: replace "using Pomerium + applicant receipt identity" with "using Pomerium + `x-pomerium-claim-discord-user-id` identity"; add Authentik Pomerium/officer blueprint or explicit modification of the existing Pomerium OAuth2 provider; add Pomerium `idp_scopes` and `jwt_claims_headers` changes; remove `/auth/discord/me` as an officer prerequisite.
- **§4 API Surface Consumed**: `/api/v1/me` should expose `groups` and, for officer surfaces, `discord_user_id` from Pomerium if present. `/auth/discord/me` remains applicant-form-only, not the actor bridge for `/applications/queue`.
- **§5 Data Flow / Signals**: route-local officer auth state becomes `checking | anonymous | non_officer | officer_missing_discord_claim | officer_verified(discord_user_id)`. There should be no "Login with Discord" applicant receipt step for officers unless the Authentik login itself redirects through Discord.
- **§6 Authorization Model**: officer with missing Pomerium Discord claim is a hard server-side auth failure; officer group alone is not authority; list/claim still require application grants on the resolved member UUID; bridge must reject synthetic/public-intake members.
- **§7 Test Plan**: replace "requires applicant receipt" tests with "requires Pomerium Discord claim"; add mismatch-proof tests that an unrelated `applicant_receipt` cookie is ignored; add static Authentik blueprint test for Pomerium `discord_user_id` scope mapping and Pomerium config test for `x-pomerium-claim-discord-user-id`.
- **§8 Anti-scope**: explicitly anti-scope `member_links`, new actor kinds, applicant receipt reuse for officer actor identity, and browser-supplied actor headers.

### Operational rollout notes

- First-time officer login should route through Pomerium to Authentik. If the officer has not linked/authenticated with Discord in Authentik, Authentik should require that source before returning to Pomerium.
- Officers should not have to authorize Discord twice in the app. The browser may still have an `applicant_receipt`, but officer endpoints ignore it.
- Pomerium session expiry controls officer login. The old applicant receipt TTL remains relevant only to `/applications` submit behavior.
- If an officer changes Discord accounts, the Pomerium `discord_user_id` claim changes; the API resolves a different member UUID, and chapter/application authority must be re-granted to that member. Old authority should be revoked during offboarding.
- If the Authentik claim is missing after deployment, fail closed and show an "officer identity incomplete" state rather than falling back to `/auth/discord/me`.

### Open questions for the orchestrator

- Where is the current Authentik `pomerium` app/provider actually created? It is referenced by Pomerium (`/application/o/pomerium/`) but not declared in the checked-in bootstrap blueprint.
- Should officer Authentik login force Discord as the only source, or allow local users only after they link a Discord source? M1 needs one of those to be product-true.
- Should `resolve_or_create_real_discord_member` create member rows for officers on first officer login, or should officers be required to already exist as members before queue access?
- Should authority grants for application review be standardized on member UUID only? The current application service uses exact `actor_id`, so Discord snowflake aliases will not help list/claim unless grants are written to the UUID.
- Should the Pomerium-forwarded claim be additionally verified from `X-Pomerium-Jwt-Assertion` inside the API, or is the existing trusted-edge header model sufficient for local/dev?
