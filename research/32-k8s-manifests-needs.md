# Synthesis: K8s GitOps Manifests — Humility Needs (NN=32)

## Context

This synthesis maps the research at `research/32-k8s-manifests.md` to
Humility's specific Phase 1 foundation deployment needs.

## Key research findings mapped to Humility

### 1. Flux bootstrap root kustomization

**Research says:** Flux bootstrap creates `gotk-components.yaml`,
`gotk-sync.yaml`, and a root `kustomization.yaml` in `flux-system/`.
The root kustomization aggregates these bootstrap artifacts. A separate
cluster/environment root can compose other bases (monitoring, secrets).

**Humility needs:** Since this repo uses `k8s/base/flux-system/` (not
Flux's default `clusters/<cluster>/flux-system/` path), the kustomization
should serve as a platform root that references the monitoring and secrets
bases. The bootstrap artifacts (`gotk-components.yaml`, `gotk-sync.yaml`)
are generated by `flux bootstrap` at deploy time, not pre-authored. This
file should use `kustomize.config.k8s.io/v1beta1` as a standard Kustomize
entry point.

### 2. Monitoring HelmRelease (kube-prometheus-stack)

**Research says:** Current chart version is `83.4.1` (app `v0.90.1`).
Upstream defaults leave resources empty, retention at 10d for Prometheus
and 120h for Alertmanager, storage/persistence disabled. No official
small-cluster sizing guide exists.

**Humility needs:** This is a 1-3 node k3s cluster on Hetzner Cloud
with `cpx21` (staging) and `cpx31` (production) instances. Phase 1 needs:
- Pin chart version `83.4.1` for reproducibility
- Set explicit resource limits (Prometheus ~512Mi-1Gi memory, Grafana
  ~256Mi, Alertmanager ~256Mi) appropriate for small nodes
- Prometheus retention: 10d base (shorter in staging overlay)
- Grafana persistence: disabled for Phase 1 (dashboards from ConfigMaps)
- `storageSpec` for Prometheus: use `emptyDir` for Phase 1 bootstrap
  (proper PVCs in Phase 2 after storage layer is stable)
- Enable `ServiceMonitor` discovery with permissive selectors

### 3. Sealed-secrets HelmRelease

**Research says:** Current chart version is `2.18.5` (app `0.36.6`).
Controller runs non-root by default. Key auto-renewal every 30 days.
Resources default empty. Minimal footprint.

**Humility needs:** This is a Phase 1 bootstrap component that will be
replaced by Infisical. Scope should be minimal:
- Pin chart version `2.18.5`
- Deploy to `sealed-secrets` namespace (already defined)
- Default security context (non-root, read-only rootfs) is sufficient
- Small resource limits (128Mi memory is plenty)
- Skip metrics ServiceMonitor for Phase 1
- No custom key rotation config — defaults are fine for bootstrap scope

### 4. Staging overlay kustomization

**Research says:** Kustomize overlays reference bases via relative paths
in `resources:`. Patches can use strategic merge, JSON merge, or inline
patches. Flux renders overlays during reconciliation.

**Humility needs:** Staging overlay should:
- Reference `../../base/monitoring` and `../../base/secrets`
- Include patches for reduced resources and shorter retention
- Match the `cpx21` instance sizing in staging terraform
- Use shorter reconciliation intervals for faster iteration

## Gaps identified

1. **No production overlay in this batch** — P0489 only covers staging.
   Production overlay (`k8s/overlays/production/kustomization.yaml`) is
   noted as a carry-over from P0480 but not in this batch's
   EXECUTE_IMPLEMENTATION scope.

2. **Bootstrap vs platform root ambiguity** — The research identifies
   that Flux bootstrap generates its own kustomization. This repo's
   `k8s/base/flux-system/kustomization.yaml` should be a platform root,
   not a bootstrap artifact replacement. The actual bootstrap artifacts
   are generated at deploy time.

## Conclusion

All four manifests are well-scoped for Phase 1 bootstrap. Chart versions
are current. The research provides sufficient evidence to proceed to
proposal.
