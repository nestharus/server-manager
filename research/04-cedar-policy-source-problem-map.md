## Known risky or brittle behavior already present

- The deployed OPAL source of truth is empty. `render-values.yaml` sets `server.policyRepoUrl: null` (`render-values.yaml:1-5`), and the rendered manifest turns that into `OPAL_POLICY_REPO_URL` with no value while polling remains enabled every 30 seconds (`rendered/opal-0.0.29.yaml:187-195`). The RCA observed current OPAL Server logs cloning an empty repository and OPAL Client receiving 503 `policy repo was not found` from `/policy` (`cedar-bootstrap-put-FINDINGS.md:16`, `cedar-bootstrap-put-FINDINGS.md:30-34`, `cedar-bootstrap-put-FINDINGS.md:50-52`).
- Policy authority is split. OPAL Server/Client are configured to use OPAL's policy-source flow (`OPAL_SERVER_URL` on the client and `OPAL_POLICY_REPO_*` on the server) (`rendered/opal-0.0.29.yaml:110-120`, `rendered/opal-0.0.29.yaml:187-195`), but the actual bundle is only mounted into a Job and written directly to Cedar Agent memory (`bootstrap-job.yaml:36-49`, `bootstrap-job.yaml:60-74`). The RCA identifies this as the root cause: OPAL cannot hydrate Cedar from its own configured source while the Job's direct PUT is not an OPAL source (`cedar-bootstrap-put-FINDINGS.md:50-52`).
- The bootstrap Job success condition is too narrow. It waits for `GET /v1/policies` to be reachable, not for a non-empty policy set, expected policy IDs, or authorization decisions after OPAL has refetched (`bootstrap-job.yaml:36-49`). The RCA notes the current tests allowed "bootstrap command exited 0" to stand in for durable hydration (`cedar-bootstrap-put-FINDINGS.md:46-48`).
- The current validators encode the brittle Job assumption. `validate_auth_stack_local.sh`, `validate_access_policy_local.sh`, `validate_tenant_isolation_local.sh`, and `verify-service-identity-claim.sh` all wait on `job/cedar-access-policy-bootstrap` before probing Cedar (`validate_auth_stack_local.sh:247-250`; `validate_access_policy_local.sh:156-158`; `validate_tenant_isolation_local.sh:206-207`; `verify-service-identity-claim.sh:106-107`). If the bootstrap Job is removed under Candidate A, these assertions no longer describe the supported path.
- The runtime proofs are immediate probes, not durability probes. They do not wait past `OPAL_POLICY_REPO_POLLING_INTERVAL=30`, assert policy IDs via `GET /v1/policies`, or restart `opal-client` before rechecking (`validate_access_policy_local.sh:162-202`, `validate_tenant_isolation_local.sh:211-246`). The RCA explicitly calls out the absence of checks after `/policy` fetch failure, after a polling interval, or after an `opal-client` restart (`cedar-bootstrap-put-FINDINGS.md:46-48`).
- The ConfigMap is a duplicated representation of the canonical policy file. Current tests enforce exact equivalence between `policy/cedar/.../policies.json` and `ConfigMap.data.policies.json` (`validate_access_policy_local.sh:106-120`, `test_access_policy_contract.py:68-79`), which keeps drift visible today but also means any source-of-truth move must update the fixture assertions that currently equate "GitOps bundle" with "ConfigMap payload."
- OPAL is configured to load `.cedar` policy modules (`render-values.yaml:6-7`, `rendered/opal-0.0.29.yaml:192-195`), while the current canonical bundle is a JSON array of policy objects (`policies.json:1-34`) and the ConfigMap data is that same JSON array (`access-policy-configmap.yaml:11-45`). This format mismatch is already present in the surface that Candidate A will consume; this map does not decide how the proposal represents it.
- The local seed flow packages one snapshot repo. `seed_git_daemon` computes one repo name, `humility-${CHANNEL_ID}.git`, and pushes one snapshot into that repo (`install-flux-for-channel.sh:168-205`). If the proposal introduces a separate policy repo rather than a path inside the existing repo, the current seed flow has no second push path.
- Remote-channel support is not present for this surface. `dev.yaml` contains access-policy contract fields (`infra/channels/dev.yaml:94-123`) but explicitly omits GitOps until remote Flux wiring is scoped (`infra/channels/dev.yaml:223`). BL-013/INIT-124 records remote public-intake apply as future work because remote channel application workload specs do not exist yet (`plans/BACKLOG.md:224-235`).

## Adjacent surfaces inside the blast radius

- FluxCD reconciliation is inside the blast radius because the selected direction uses the same in-cluster git daemon that Flux already consumes. Flux currently watches `humility-local.git` and `./gitops/channels/local` (`infra/channels/local.yaml:20-32`), and the renderer emits a single `GitRepository` plus `Kustomization` from that channel contract (`render-gitops-source.py:104-172`). A policy source under the same repo but outside `./gitops/channels/local`, or a second repo, changes what has to be present in the seeded Git daemon even if Flux's watched path does not change.
- The git-daemon seed flow is directly adjacent. The Deployment can serve any bare repo under `/srv/git` through the CGI endpoint (`git-daemon.yaml:100-116`), but `install-flux-for-channel.sh` seeds only `/srv/git/humility-local.git` (`install-flux-for-channel.sh:168-205`). The proposal must account for this existing one-repo behavior without assuming an unimplemented second seed path.
- The `render-gitops-source.py` snapshot boundary is adjacent because it copies only `gitops/` into `.tmp/gitops-source/<channel>` (`render-gitops-source.py:74-80`, `render-gitops-source.py:208-210`). The canonical Cedar policy files currently live under top-level `policy/`, outside that copied tree (`policies.json:1-34`). Under Candidate A, source placement relative to the seeded snapshot is a real current-state constraint.
- OPAL/Cedar manifests are inside the blast radius. The rendered OPAL manifest contains both the empty server policy-source env vars and the client Cedar-store env vars (`rendered/opal-0.0.29.yaml:107-120`, `rendered/opal-0.0.29.yaml:187-195`), and the Kustomization includes both the ConfigMap and Job (`kustomization.yaml:4-7`).
- Access-policy contract tests and validators are inside the blast radius. The access-policy fixture names the repo policy file, service identity file, and ConfigMap path (`access_policy_matrix.yml:39-45`), and tests currently assert the ConfigMap loads the contract policy set (`test_access_policy_contract.py:43-79`). The Phase 6 access-policy validator currently assumes a ConfigMap-driven bundle and a rendered bootstrap Job (`validate_access_policy_local.sh:106-123`).
- Auth-stack validation is adjacent because INIT-114's validator asserts the bootstrap Job exists and uses it as the runtime loading gate (`validate_auth_stack_local.sh:134-143`, `validate_auth_stack_local.sh:247-263`).
- Pomerium/Authentik flows are adjacent because protected API traffic reaches the API through Pomerium and then depends on Cedar for `api:read` (`gitops/channels/local/auth/pomerium/ingress.yaml:31-59`, `services/api/app/api/v1/endpoints/protected.py:20-86`). Authentik/Pomerium credential material is not the policy-source surface, but failed Cedar hydration turns protected API requests into Cedar deny or unavailable responses.
- INIT-120 public-intake Cedar entries are inside the blast radius because `public-intake-allow` and `public-intake-no-read` are part of the current eight-policy bundle (`policy/cedar/channels/local/services/server-manager-api/policies.json:10-17`, `gitops/channels/local/auth/opal-cedar/access-policy-configmap.yaml:22-28`) and the public route depends on Cedar authorization before accepting submissions (`services/api/app/services/authorization.py:24-39`, `services/api/app/api/v1/endpoints/applications/public.py:21-38`).
- Tenant isolation policy substrate is inside the blast radius because tenant allow policies live in the same bundle (`policies.json:22-33`, `access-policy-configmap.yaml:33-44`), and runtime tenant isolation proof posts same-tenant/cross-tenant decisions to Cedar (`validate_tenant_isolation_local.sh:206-246`).
- Service identity claims are adjacent because Buildkite and Crossplane principals live in the same Cedar bundle (`policies.json:6-20`), INIT-115 proposed those machine identities as part of the access-policy contract (`plans/proposals/init-115-access-policy.md:9-19`), and `verify-service-identity-claim.sh` uses Cedar to prove Buildkite deploy authorization (`verify-service-identity-claim.sh:55-127`).

## Deployment mode and cohort

- Deployment mode for this slice is local channel first: `infra/channels/local.yaml` targets `k3d-local` (`infra/channels/local.yaml:8-12`) and has a live GitOps source pointed at `humility-local.git` (`infra/channels/local.yaml:20-32`).

## Open questions for proposal

- Should OPAL read Cedar policy from a sub-path inside the already-seeded `humility-local.git`, or from a separate bare repo served by the same git daemon? Current evidence: Flux and seed flow use one repo (`infra/channels/local.yaml:20-32`, `install-flux-for-channel.sh:168-205`), while the git daemon itself can serve any repo under `/srv/git` (`git-daemon.yaml:100-116`). The choice affects seed flow and source placement.
- If the selected path is inside `humility-local.git`, where should the policy source live relative to the current snapshot boundary? Current evidence: `render-gitops-source.py` copies only `gitops/` into the seeded snapshot (`render-gitops-source.py:74-80`, `render-gitops-source.py:208-210`), while canonical Cedar policies live under top-level `policy/` (`policies.json:1-34`).
- What exact bundle format should OPAL serve to Cedar from Git? Current evidence: OPAL is configured to watch `.cedar` extensions (`render-values.yaml:6-7`, `rendered/opal-0.0.29.yaml:192-195`), but the current canonical bundle and ConfigMap are JSON arrays of `{id, content}` objects (`policies.json:1-34`, `access-policy-configmap.yaml:11-45`).
- Which validation artifact becomes the replacement for ConfigMap equality? Current evidence: `validate_access_policy_local.sh`, `test_access_policy_contract.py`, and `test_public_intake_policy_fixture.py` currently assert ConfigMap-driven bundle shape (`validate_access_policy_local.sh:106-120`, `test_access_policy_contract.py:43-79`, `test_public_intake_policy_fixture.py:96-105`).
- Which runtime signal should replace bootstrap Job completion as the local loaded-policy gate? Current evidence: all existing runtime validators wait on `job/cedar-access-policy-bootstrap` (`validate_auth_stack_local.sh:247-250`, `validate_access_policy_local.sh:156-158`, `validate_tenant_isolation_local.sh:206-207`, `verify-service-identity-claim.sh:106-107`), while the RCA requires proving declared policy-source hydration rather than Job completion (`cedar-bootstrap-put-FINDINGS.md:68-75`).
