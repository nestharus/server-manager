# FA Pro+ / WA Pro agent integration - findings

Date: 2026-04-27.

## Headline verdict

- Font Awesome is partly automatable today.
- Font Awesome package installs are automatable with a package manager token.
- Font Awesome GraphQL can read public metadata, releases, searches, account kits, and kit metadata.
- Font Awesome GraphQL can initiate and poll kit downloads only with a token that has the required download scope.
- Public Font Awesome docs do not expose kit create/update/delete/rotate mutations.
- Current self-service Font Awesome API tokens are documented as `public` plus `kits_read`.
- The only documented GraphQL mutation is `createKitDownload`.
- Therefore kit CRUD, custom icon upload, kit package enablement, and kit code rotation are web-UI-only unless Font Awesome Support grants private write scopes.
- Web Awesome Pro is package-install automatable after the user provides workspace package credentials.
- Public Web Awesome docs do not expose REST, GraphQL, or CLI management APIs.
- Web Awesome workspace/project creation, hosted project configuration, theme builder, Pro asset website downloads, and seats are web-UI-only.
- Infisical is compatible with the desired handoff.
- INIT-103 makes Infisical the runtime secret store; use it for FA and WA tokens.

## FontAwesome Pro+

### Account / tier

- Account dashboard: `https://fontawesome.com/account`.
- Kits dashboard: `https://fontawesome.com/kits`.
- Tokens live under the Font Awesome Account Tokens section.
- Font Awesome documents two token classes.
- Package manager tokens install Pro/Pro+ assets with package managers.
- API tokens access account, kit, and icon data through APIs.
- Pro+ is confirmed as the subscription level required for Pro+ icon packs.
- Official v7 docs say Pro+ icon packs are curated sets with unique visual styles.
- Official v7 docs say each Pro+ pack contains around 200 common app/website icons.
- Official v7 docs say those packs are only available with a Pro+ subscription.
- Current Pro+ packs/styles documented include Chisel, Etch, Graphite, Jelly, Notdog, Slab, Thumbprint, Utility, and Whiteboard.
- I did not find official evidence that Pro+ is the highest current Font Awesome tier.
- Web Awesome's Terms of Service mention `Pro Lite+`, `Pro+`, and `ProMax+`; do not assert "Pro+ is highest" without direct Font Awesome plan evidence.
- I found no public Font Awesome seat/user management API.
- Treat seat/user management as dashboard administration.

### Kit Management API (yes/no, scope, auth)

- API endpoint: `https://api.fontawesome.com`.
- API style: GraphQL.
- Token exchange endpoint: `https://api.fontawesome.com/token`.
- Auth flow:
- User generates an API Token in the account dashboard.
- Agent stores it as `FA_API_TOKEN`.
- Agent POSTs to `/token` with `Authorization: Bearer <FA_API_TOKEN>`.
- Font Awesome returns a short-lived GraphQL access token.
- The documented example access token lifetime is 3600 seconds.
- GraphQL calls use `Authorization: Bearer <access_token>`.
- Unauthenticated GraphQL supports public metadata such as release lookup.
- Authenticated GraphQL supports `me`.
- `me { kits { ... } }` lists kits for the account.
- `me { kit(token: "...") { ... } }` reads one kit.
- Kit fields documented include `name`, `token`, `status`, `licenseSelected`, `technologySelected`, `version`, `minified`, `domains`, `autoAccessibilityEnabled`, `shimEnabled`, `iconUploads`, and `release`.
- Documented self-service scopes are `public` and `kits_read`; other documented scopes include `kits_download`, `profile_read`, `domains_read`, `svg_icons_pro`, and `svg_icons_free`.
- Font Awesome docs say only `public` and `kits_read` can currently be generated by account holders from the account page.
- Font Awesome docs say to contact Support for other scopes.
- Supported kit read operation: yes, with `kits_read`.
- Supported kit download operation: yes in GraphQL schema, but token scope may require Support.
- Supported create kit operation: no public documented mutation found.
- Supported update kit operation: no public documented mutation found.
- Supported delete kit operation: no public documented mutation found.
- Supported rotate kit code operation: no public documented mutation found.
- Supported enable npm package installation: no public documented mutation found.
- Web UI kit settings include name, type, tech, embed method, subset, styles, version, domain limits, compatibility, npm package enablement, and conflict detection.
- Rate limits: kit download polling should be no more than once per second; I found no broader numeric public rate-limit table.
- Examples: official docs show direct `curl` GraphQL calls and recommend GraphiQL clients for schema exploration.
- I found no official Font Awesome kit-management CLI.

### npm Pro registry auth

- Registry: `https://npm.fontawesome.com/`.
- Required `.npmrc`: `@fortawesome:registry=https://npm.fontawesome.com/`, `@awesome.me:registry=https://npm.fontawesome.com/`, and `//npm.fontawesome.com/:_authToken=${FONTAWESOME_PACKAGE_TOKEN}`.
- Store the underlying value in Infisical as `FA_NPM_TOKEN`.
- Export it as `FONTAWESOME_PACKAGE_TOKEN` only for install/update commands.
- Do not commit resolved tokens.
- Font Awesome docs call this a package manager token.
- The public docs reviewed do not distinguish account-wide from CI-only package tokens.
- Token rotation is dashboard-controlled; docs say tokens can be refreshed/replaced if compromised.
- Kit package install: `@awesome.me/kit-KIT_CODE@latest`.
- Pro SVG packages include `@fortawesome/fontawesome-svg-core`, Classic Pro packages, Duotone packages, Sharp packages, and Sharp Duotone packages.
- All-inclusive package: `@fortawesome/fontawesome-pro`.
- Font Awesome docs say `@fortawesome/fontawesome-pro` does not include Pro+ icons.
- Use Kit Packages for Pro+ packs and custom kit icons unless account docs expose a separate Pro+ package path.

### Pro+ specific asset handling

- Pro+ packs are small-batch and not full parity with larger packs.
- Documented Pro+ prefixes include `facr`, `faes`, `fagt`, `fajr`, `fajfr`, `fajdr`, `fans`, `fands`, `faslr`, `faslpr`, `fatl`, `fausb`, `faufsb`, `faudsb`, and `fawsb`.
- Custom Kit icons can be included in Kits and Kit Packages; custom prefixes include `fak` and `fakd`.
- Upload requirements: SVG only, `viewBox` required, monotone uses one path, duotone uses two paths with opacity.
- Programmatic custom icon upload: no public documented API found.
- Upload remains web UI only today.

### Solid integration pattern

- I found no official Font Awesome Solid/SolidJS component in current official docs.
- Use `@fortawesome/fontawesome-svg-core` directly.
- Use individual Pro SVG package imports for tree-shaking.
- Or use `@awesome.me/kit-KIT_CODE` when the project needs Pro+ packs or uploaded custom icons.
- Font Awesome docs say SVG Core is side-effect free.
- Font Awesome docs say SVG Core is suitable as a base for framework integrations.
- Font Awesome docs say icon packages support tree shaking.
- Solid 2 pattern: import icon definitions, call `icon(iconDefinition).abstract`, and convert the abstract tree to Solid JSX.
- Avoid `innerHTML` unless all icon inputs are trusted.
- Avoid `dom.watch()` for Solid-rendered components unless the project intentionally uses `<i>` replacement.
- For Kit Packages, prefer individual icon import paths over broad `all` or pack imports.
- Kit "By Icon" subsetting can also reduce payload for kit packages.

### One-time human steps

- Sign into `https://fontawesome.com/account`, confirm active Pro+, generate `FA_NPM_TOKEN`, and generate `FA_API_TOKEN`.
- If using kits, create the initial kit in the web UI.
- Configure Pro/Pro+ styles, SVG or Web Fonts, version, domains, and package installation.
- Copy `FA_KIT_CODE`.
- Upload custom/private icons in the dashboard if needed.
- Ask Font Awesome Support for `kits_download` if automated kit downloads are required.
- Ask Font Awesome Support whether kit write scopes exist if automated kit CRUD is required.
- Store resulting tokens and codes in Infisical.

### Recurring agent operations

- Exchange `FA_API_TOKEN` for short-lived GraphQL access tokens.
- Read release metadata, icon metadata, and kit metadata.
- Install/upgrade Pro packages and Kit Packages; update lockfiles.
- Generate token-free `.npmrc` and client-safe environment config from Infisical.
- Download kits only if a sufficiently scoped token exists.
- Detect missing web UI settings and produce exact dashboard instructions.
- Cannot create/update/delete/rotate kits through the public documented API.

## WebAwesome Pro

### Account / tier / license

- Login URL: `https://webawesome.com/login`.
- Purchase URL: `https://webawesome.com/purchase`.
- Web Awesome is a Fonticons product associated with Font Awesome.
- The Pro purchase page describes a subscription plan.
- Pro includes Pro components, layout tools, patterns, hosted projects, themes, theme builder, color tools, Figma design kit, WA Pro perpetual license, and support.
- Seat model: the purchase page exposes seats; the Pro license defines Seat Count as purchased seats and allows that many Creators.
- Removing a Creator requires that person to stop using Pro Assets and remove local copies.
- License keys must be kept confidential under the Pro license.
- I found no public runtime or build-time license validation API.
- Relationship to Font Awesome: Web Awesome integrates Font Awesome kit codes for Pro/Pro+ icons, but public docs do not prove credentials are interchangeable.
- Treat them separately unless the dashboard proves shared credentials.

### Programmable operations (yes/no/scope)

- Public REST API: none found.
- Public GraphQL API: none found.
- Public workspace/project CLI: none found.
- Public package install: free package `@awesome.me/webawesome`; Pro package `@awesome.me/webawesome-pro`.
- Public docs say Pro users install `@awesome.me/webawesome-pro` and consult workspaces for details.
- Hosted projects provide a personal CDN; updating project settings updates what project code pulls in.
- Public docs instruct users to sign up/log in, create a project, and copy the project code.
- No project CRUD API found.
- Theme Builder: public docs point to project settings and Theme Builder; no API found.
- Pro-gated components/patterns include Combobox, File Input, Page, Toast, Data Visualization, Pro layouts/patterns, and Figma Design Kit.
- Unlock model: hosted Project under a Pro workspace for CDN/autoloading, or `@awesome.me/webawesome-pro` for npm/self-hosting.
- Font Awesome Pro+ icons in `<wa-icon>` require a Font Awesome kit code.

### npm Pro registry auth

- Package source: `@awesome.me/webawesome-pro`.
- Public docs hide Pro install details behind the user's workspaces.
- Font Awesome package docs map the `@awesome.me` scope to `https://npm.fontawesome.com/`.
- Expected registry is therefore `https://npm.fontawesome.com/` unless workspace instructions say otherwise.
- Store as `WA_NPM_TOKEN` in Infisical.
- Do not assume `FA_NPM_TOKEN` and `WA_NPM_TOKEN` are the same.
- If the same token works for both, keep the names separate for rotation clarity.
- CI portability: public docs do not describe machine-bound installs; package token access is the CI-compatible model.
- Seat enforcement appears legal/account based in the public license, not machine-bound in public npm docs.

### Pro Asset Packs handling

- Pro Asset Packs include patterns and themes not in Web Awesome Free.
- They include premium variants of free components in different styles.
- Pro Software includes online services for design/development workflows.
- The Pro license says current Pro Assets and Pro Software are available to download via the Website while the agreement continues.
- I found no public programmatic Pro Asset Pack download API.
- If assets ship inside `@awesome.me/webawesome-pro`, agents can fetch them through package install/pack.
- If assets are website-only downloads, they remain manual.
- Prefer package-managed assets over committed downloaded Pro asset archives.
- Do not commit Pro tarballs unless repo visibility and license review explicitly allow it.

### Per-component Pro flags

- Public docs label Pro components and patterns in the docs navigation.
- No compile-time `WA_LICENSE_KEY` flag found.
- No runtime license validation call found.
- The practical unlock is package/workspace access.
- For Font Awesome icons in Web Awesome, add `data-fa-kit-code` or call `setKitCode()`.
- Store `WA_LICENSE_KEY` only if the dashboard exposes one and package/build tooling consumes it.

### One-time human steps

- Sign into Web Awesome, confirm Pro subscription and seat count, and assign Creators/seats in the web UI.
- If using hosted projects, create the workspace/project, configure version/theme/color/FA kit code, and copy project code.
- If using npm, open workspace package instructions, copy the `@awesome.me/webawesome-pro` token/instructions, and store `WA_NPM_TOKEN` in Infisical.
- Store `WA_LICENSE_KEY` only if required by workspace/package instructions.
- Download website-only Pro Asset Packs manually if package-managed assets do not cover the need.

### Recurring agent operations

- Install/upgrade `@awesome.me/webawesome-pro`, update lockfiles, and verify Pro component imports.
- Add Web Awesome Pro components and `data-fa-kit-code` or `setKitCode()` wiring.
- Generate `.npmrc` and client-safe Vite env files from Infisical.
- Inspect installed package contents for exact asset paths.
- Cannot create/configure Web Awesome projects through public documented APIs.
- Cannot manage seats through public documented APIs.
- Cannot download website-only Pro Asset Packs through public documented APIs.

## Credential vault integration

### Infisical project + secret list

- Local project rule: INIT-103 establishes Infisical as runtime secret store; SOPS+age is bootstrap-only.
- Recommended Infisical project: `platform-frontend`.
- Recommended environments: `dev`, `staging`, `production`.
- Recommended paths: `/fontawesome`, `/webawesome`, and `/frontend/build`.
- Secrets: `/fontawesome/FA_NPM_TOKEN`, `/fontawesome/FA_API_TOKEN`, `/fontawesome/FA_KIT_CODE`, `/webawesome/WA_NPM_TOKEN`, and `/webawesome/WA_LICENSE_KEY` only if applicable.
- Optional build alias: `/frontend/build/FONTAWESOME_PACKAGE_TOKEN`.
- Optional client-safe value: `/frontend/build/VITE_FA_KIT_CODE`.
- Infisical Operator: official docs say it syncs Infisical secrets into Kubernetes through `InfisicalSecret`.
- `InfisicalSecret` supports Kubernetes auth with machine identity; `managedKubeSecretReferences` defines generated Kubernetes Secret targets.
- Runtime frontend should not receive npm/API/license tokens.
- Only dependency install/build jobs need package tokens.

### .npmrc pattern

```ini
@fortawesome:registry=https://npm.fontawesome.com/
@awesome.me:registry=https://npm.fontawesome.com/
//npm.fontawesome.com/:_authToken=${FONTAWESOME_PACKAGE_TOKEN}
```

- Commit only the token-free form.
- Generate local or CI env vars from Infisical.
- Use `FA_NPM_TOKEN` for Font Awesome package installs.
- Use `WA_NPM_TOKEN` for Web Awesome Pro package installs unless workspace docs prove the same token is valid.
- Use temp generated files with mode `0600` when a concrete `.npmrc` is unavoidable.
- Remove token-bearing generated files after install when feasible.

### Setup-time script outline

- Script: `scripts/bootstrap-frontend-pro-secrets.sh`.
- Inputs: Infisical project `platform-frontend`, environment slug, and secret path selector.
- Actions: authenticate to Infisical, read FA/WA secrets, validate selected mode, export `FONTAWESOME_PACKAGE_TOKEN`, write token-free or temporary `.npmrc`, write client-safe `apps/web/.env.local`, run install/update, and unset package token.
- Confirm no secret is written to Vite client env names.
- CI variant: Buildkite reads Infisical; token exists only during dependency install.
- Build and tests run after token unset where possible.

### Rotation cadence

- Rotate package tokens on offboarding, suspected leakage, CI compromise, or quarterly.
- Rotate API tokens on suspected leakage or quarterly.
- Refresh GraphQL access tokens per run; they are short-lived.
- Rotate kit code only after exposure or pageview abuse.
- Rotate WA license key according to vendor capability if one exists.
- After rotation: update Infisical, run install smoke check, run frontend build, and search repo/logs/bundles for leaked token values.

## Agent handoff design

### Concrete one-time human action list

- Font Awesome: confirm active Pro+, create/copy Package Manager Token and API Token, create initial Kit if used, configure styles/tech/version/domains/package install, copy Kit Code, and upload custom icons if needed.
- Web Awesome: confirm Pro subscription and seats/Creators, create workspace/project if hosted CDN is used, copy Pro package token/instructions, and copy license key only if exposed.
- Infisical: create `platform-frontend`, add `dev`/`staging`/`production`, store `FA_NPM_TOKEN`, `FA_API_TOKEN`, `FA_KIT_CODE`, `WA_NPM_TOKEN`, and optional `WA_LICENSE_KEY`, then grant CI/agent read access only to needed paths.
- Optional Support: request `kits_download` for automated kit downloads and ask whether kit write scopes exist for CRUD automation.

### Concrete recurring agent capability list

- Install FA Pro packages, FA Kit Packages, and WA Pro package.
- Upgrade package versions and lockfiles.
- Generate `.npmrc` and env files from Infisical.
- Read FA releases, icon metadata, and kit metadata; refresh GraphQL access tokens.
- Download kit zips if a scoped token exists.
- Add Solid/Vite integration code, Web Awesome Pro imports, and `setKitCode()` or `data-fa-kit-code`.
- Verify private package access and validate no secrets are committed or bundled.

### Honest list of operations that remain web-UI-only

- Font Awesome: first token generation, kit creation, kit settings edits, kit package enablement, custom/private icon upload, kit deletion, kit code rotation unless a private API exists, and account billing/seat/user administration.
- Web Awesome: account/workspace/project creation, hosted project settings, Theme Builder changes, seats/Creators, first Pro package credential retrieval, website-only Pro Asset Pack downloads, and billing/subscription administration.
