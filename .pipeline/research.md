# INIT-105 Phase 1 Research: TLS and DNS Automation

## Scope and Sources

- **Binding row**: INIT-105 owns TLS and DNS automation after INIT-102 Flux and INIT-103 Infisical, with INIT-104 MinIO available as the local service to prove DNS resolution.
- **Official cert-manager evidence**: The current cert-manager Helm documentation says the OCI chart is the source of truth and shows `helm template ... --set crds.enabled=true` as the static-manifest path.
- **Official Smallstep evidence**: The step-certificates chart deploys step-ca and supports bootstrap-generated CA material; the Step Issuer project is the cert-manager CertificateRequest controller that signs via step-ca.
- **Official ExternalDNS evidence**: The Cloudflare provider supports API token authentication through `CF_API_TOKEN`, TXT registry ownership, domain filters, and dry configuration without applying records.
- **Official ACME evidence**: cert-manager ACME ClusterIssuers support Let's Encrypt staging and production directory URLs; staging is the only remote ACME endpoint in scope.
- **K3d and CoreDNS evidence**: k3s includes CoreDNS in kube-system; INIT-105 can layer a local domain rewrite into the Corefile for cluster-internal names.

## cert-manager Raw Manifest Research

- **Install method**: Use `helm template cert-manager oci://quay.io/jetstack/charts/cert-manager --version v1.20.2 --namespace cert-manager --set crds.enabled=true` and commit the output.
- **Namespace gap**: The Helm template output does not create the namespace; add a separate Namespace manifest in the Kustomize subtree.
- **CRD ownership**: CRDs must be in the raw render so Certificates, CertificateRequests, Issuers, and ClusterIssuers exist before sample objects reconcile.
- **No helm-controller**: No HelmRelease, HelmRepository, OCIRepository, or runtime chart reconciliation is introduced.
- **Readiness**: Cluster proof waits on cert-manager controller, webhook, and cainjector deployments before expecting issuance.
- **Version pin**: Pin cert-manager app and chart to v1.20.2; this is compatible with the k3s v1.32 channel because the chart supports Kubernetes >=1.22.

## step-ca and Step Issuer Research

- **step-ca chart**: Use smallstep/step-certificates chart 1.30.1, app 0.30.2, rendered to raw YAML.
- **ACME provisioner**: The chart bootstrap supports `ca.bootstrap.postInitHook`; INIT-105 can add an ACME provisioner for future compatibility while local issuance uses Step Issuer.
- **Why Step Issuer**: cert-manager built-in ACME would require HTTP-01 ingress or DNS-01 provider plumbing, both outside local scope; Step Issuer signs CertificateRequests directly through step-ca.
- **Cluster issuer shape**: Create a cluster-scoped `StepClusterIssuer` named `humility-local-step-ca` after step-ca bootstraps its root and provisioner metadata.
- **Dynamic config**: A post-bootstrap Kubernetes Job reads the generated root CA and provisioner kid from step-ca ConfigMaps and applies the StepClusterIssuer.
- **Secret boundary**: The provisioner password Secret is generated by the step-ca bootstrap chart in `step-ca-system`, not SOPS.

## CoreDNS Local Domain Research

- **Default owner**: k3s owns the CoreDNS deployment in kube-system; GitOps can own the CoreDNS ConfigMap as the local channel contract.
- **Domain**: Use `humility.local` for local-only cluster DNS; it is not a public Cloudflare zone.
- **Rewrite**: CoreDNS rewrite maps `name.namespace.humility.local` to `name.namespace.svc.cluster.local` and rewrites answers back.
- **Proof target**: Use existing MinIO service as a stable local service: `minio.minio-system.humility.local`.
- **Risks**: Replacing the Corefile can drift from k3s defaults; keep the Corefile close to k3s default and limit custom behavior to the rewrite block.

## ExternalDNS Cloudflare Research

- **Provider**: ExternalDNS chart 1.20.0, app 0.20.0, provider `cloudflare`, image `registry.k8s.io/external-dns/external-dns:v0.20.0`.
- **Credentials**: Use `CF_API_TOKEN` from a Kubernetes Secret generated by Infisical, with no SOPS secret for Cloudflare.
- **Registry**: Use TXT registry and a channel-specific owner id to prevent record ownership collisions.
- **Policy**: Use `upsert-only` in the contract so deletion is a later explicit remote-deployment decision.
- **Apply boundary**: Remote manifests live under `gitops/contracts/remote/tls-dns` and are not referenced by the local Kustomization.

## ACME Remote Research

- **Endpoint**: Use Let's Encrypt staging endpoint `https://acme-staging-v02.api.letsencrypt.org/directory`.
- **Solver**: Use DNS-01 Cloudflare solver with the same Infisical-backed token Secret.
- **No issuance**: No Certificate references the remote ACME issuer in INIT-105.
- **Production**: Production endpoint remains a handoff item after remote DNS, ingress, and deployment ordering are decided.

## Toolchain Check

- **Required existing tools**: kubectl and helm remain required; k3d/docker are required for cluster proof.
- **step CLI**: The host `step` CLI is useful for diagnostics but not required by the automated harness because step-ca and the issuer configuration run in-cluster.
- **cmctl**: cmctl is useful for human cert-manager debugging but not required by the harness.

## Risks and Open Questions

- **R1**: Step Issuer adds one controller beyond the initial noun list, but it is the narrow adapter that lets cert-manager requests be signed by step-ca without ingress.
- **R2**: CoreDNS ConfigMap ownership can conflict with k3s defaults; harness must prove default cluster DNS and the local rewrite still work.
- **R3**: Remote Cloudflare domain is placeholder contract material until a real zone is recorded in DECISIONS.md.
- **R4**: Let's Encrypt staging issuer must not be used to request certificates before public ingress and DNS exist.
- **Open question**: INIT-106 should decide whether remote DNS domain names move from placeholder contract to a real Cloudflare zone name.
