## Tension Resolutions Needed

### P15 (Traceability as Outcome) vs P1 (Operator Clarity) for cross-subsystem queries

- **Principles in tension:** Principle 15 (Traceability as Outcome) — cross-subsystem connections use event correlation with shared identifiers, not foreign key navigation at the data layer. Principle 1 (Operator Clarity) — operators must always understand what the system is doing and be able to query operational state, including cross-subsystem views like "what is this member's full operational history?"
- **Context where they conflict:** When an operator needs to trace a member's full operational history across subsystems (intake, tickets, chapter membership, compliance, audit), P15 requires event-based correlation while P1 demands that the answer be readily accessible. Event correlation may require multiple query steps, specialized tooling, or an aggregation layer to match the simplicity of a single FK-based join. The philosophy currently lists P15+P1 as reinforcing ("operators can reconstruct any causal chain"), which is true in the abstract but assumes event-based traceability is equally ergonomic for operators as FK navigation. The proposal's choice of FK joins over event correlation demonstrates the practical pull: proposers will predictably choose FK joins because P1's demand for operator-facing simplicity is more immediately felt than P15's demand for architectural independence.
- **Option A: Optimize for P15 (subsystem independence).** Cross-subsystem queries use event correlation as P15 prescribes. Operators use query tooling designed for event correlation (trace viewers, correlation-ID-based lookups, event search). The system invests in making event-correlation queries ergonomic rather than providing FK-join shortcuts. This preserves the three reinforcing interactions P15 protects (P15+P12 subsystem independence, P15+P5 low lock-in, P15+P10 durable events). Cost: cross-subsystem queries are inherently more complex to build and maintain; operator query ergonomics depend on the quality of correlation tooling rather than direct relational navigation.
- **Option B: Optimize for P1 (operator query simplicity).** Allow FK-based cross-subsystem joins where they serve common operator queries. Accept the coupling cost in exchange for simple, fast, complete query paths. Cost: weakens the three interactions P15 protects — schema evolution in one subsystem can affect queries and constraints in referencing subsystems; replacing or restructuring a subsystem requires updating all subsystems that reference its objects.
- **Option C: Read-layer resolution.** Subsystem write-paths remain independent (no cross-subsystem FKs in operational tables). A read-optimized aggregation layer (materialized views, denormalized read models, or a dedicated query service) provides FK-join-equivalent query performance over correlated events. Operators interact with the read layer; subsystem internals remain decoupled. Cost: additional system complexity in building and maintaining the read layer; the aggregation layer must be kept in sync with events. The write-path vs read-path distinction must be consistently enforced.
- **Option D: Query-tier differentiation.** Classify cross-subsystem queries by frequency and operational importance. High-frequency operational queries (e.g., "member's full history," "all open cases for this chapter") get materialized views or dedicated query abstractions that pre-correlate events. Rare queries use direct event correlation. Cost: requires upfront classification of query patterns; the boundary between "common enough for a materialized view" and "rare enough for event correlation" is a judgment call that must be revisited as operator needs evolve.
- **Recommendation:** Option C or D. Both preserve P15's architectural guarantees at the write layer while satisfying P1's query ergonomics at the read layer. Option C is more principled (clean separation, consistent rule); Option D is more pragmatic (materialized views only where the query frequency justifies the maintenance cost). The key insight common to both: the tension resolves by distinguishing the write-path (where subsystem independence matters for P15, P12, P5) from the read-path (where operator ergonomics matter for P1). The philosophy should add a tension entry stating that P15 and P1 conflict when event-based cross-subsystem traceability imposes query complexity costs on operators, and that the resolution is to maintain subsystem independence at the data layer while providing operator-ergonomic read paths through an aggregation or materialization layer.
