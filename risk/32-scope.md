# Risk Assessment: Scope — K8s GitOps Manifests

## Verdict: LOW

## Findings

1. **Well-bounded deliverable (LOW).** The proposal produces exactly four
   YAML files using well-understood Kustomize and Flux HelmRelease
   patterns. It builds on existing infrastructure — namespaces,
   HelmRepositories, and base kustomizations are already committed. The
   manifest-only scope avoids controller configuration, bootstrap
   commands, and application workloads.

2. **Anti-scope is explicit and specific (LOW).** Production overlay, Flux
   Kustomization CRDs, GitRepository objects, durable PVC-backed storage,
   external ingress/auth, sealed-secrets key backup, and the Infisical
   migration path are all named as out of scope. This prevents ambiguity
   about what the batch does and does not include.

3. **Staging overlay exists on disk but is not yet reconcilable (LOW).** No
   Flux `Kustomization` CRD points at `k8s/overlays/staging/`, so the
   overlay cannot be reconciled by Flux until a follow-on batch creates
   that CRD. The proposal acknowledges this explicitly: "Do not author a
   separate Flux `Kustomization` CRD in this batch." This is a clean
   deferral, not a gap — the manifests are valid Kustomize and can be
   tested with `kustomize build` before Flux wiring exists.

4. **Sealed-secrets key backup deferred creates a narrow operational gap
   (LOW-MEDIUM).** The anti-scope excludes key backup/restore, but the
   research notes that sealed-secrets creates an ongoing key-backup
   obligation from the moment the controller is installed. In Phase 1 the
   cluster is pre-production, so the blast radius of key loss is small,
   but the gap should be closed before any real secrets are sealed.

5. **Detailed resource budgets are maintenance-proportional (LOW).** The
   proposal specifies explicit CPU/memory requests and limits for seven
   sub-components across base and staging. This is verbose but not
   complex — the values are one-time choices that only need revisiting on
   chart upgrades. The alternative (inheriting upstream's empty defaults)
   would leave the small k3s cluster unbounded, which the research
   identifies as the worse outcome.

6. **Downstream work is intentional and bounded (LOW).** The batch
   creates known follow-on items: production overlay, Flux Kustomization
   CRDs for environment reconciliation, PVC-backed monitoring storage,
   and sealed-secrets key backup. Each is independently scoped and none
   requires reworking the manifests this batch produces — the base/overlay
   structure supports additive extension without retroactive changes.

7. **No future-blocking design choices (LOW).** Permissive
   ServiceMonitor/PodMonitor selectors allow future cluster components to
   be observed without reworking the base release. The sealed-secrets
   controller is treated as temporary bootstrap infrastructure with no
   deep integrations that would complicate later removal. The staging
   overlay patches environment deltas only, preserving base stability.

8. **Bootstrap root mixes generated and authored content (LOW).** The Flux
   bootstrap root references both `gotk-components.yaml`/`gotk-sync.yaml`
   (generated by Flux bootstrap) and `../monitoring`/`../secrets`
   (hand-authored bases). The proposal acknowledges this tradeoff and
   justifies it: the scope is still small and explicit. For Phase 1 with
   only two platform bases, this is manageable; it becomes a concern only
   if the resource list grows significantly in later phases.

## Justification

The proposal scope is tightly bounded: four manifest files, two
HelmReleases for well-understood charts, one bootstrap root, and one
thin staging overlay. It builds on existing committed infrastructure
rather than greenfielding an entire GitOps layout. Every deferral is
named explicitly in the anti-scope section, and the downstream work it
creates is additive — nothing in this batch needs to be reworked to
support production overlays, Flux CRDs, or the Infisical migration.

The only finding above LOW is the sealed-secrets key backup gap, which
is real but narrow: the cluster is pre-production in Phase 1, so key
loss would not destroy production secrets. The gap needs closing before
real secrets are sealed but does not inflate the risk of this particular
batch.

Complexity is proportional to value. The batch delivers the minimum
viable GitOps manifest foundation — monitoring, secrets management,
bootstrap root, and an environment overlay — without over-engineering
for hypothetical future requirements or under-scoping in ways that would
force rework.
