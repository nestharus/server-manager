## 1. Scope and source corpus

This merged index covers the broader platform substrate implied by the four legacy decomposition indexes, then narrows that substrate to the minimum path required to run `server-manager` as a single application on that platform. It is a merge and conflict-resolution artifact, not an implementation plan, PR slice list, or deployment runbook.

Primary sources: `auth-v5-index`, `expansion-plan-index`, `gitops-index`, `platform-v2-index`.

Secondary sources used only to sharpen merge decisions: `complete-stack-architecture`, `roadmap-mvp`, `proposal-report`, `container-infra-analysis`, `risk-railway`.

Interpretation rule used throughout:
- `Explicit:` means the source documents directly state the fact or product choice.
- `Inference:` means the merge is reconciling conflicting sources, applying the user overrides, or narrowing the platform to the minimum viable path for `server-manager`.

## 6. Minimum viable platform for server-manager

| Capability | Why server-manager needs it | Minimal acceptable implementation |
| --- | --- | --- |
| Long-running managed compute | The bot must stay connected to Discord and process work continuously | One managed service/runtime capable of running a single always-on worker process |
| Durable `PostgreSQL` | The project rules prohibit SQLite and the bot needs persistent state | One managed Postgres instance with a single application database |
| Schema migration execution | The bot cannot rely on hand-edited schema changes | One standardized migration tool executed before or during deploy in a controlled step |
| Secret injection | Discord token, guild ID, DB URL, and future service credentials must never be interactive or baked into the image | Provider/runtime secret variables or equivalent secure injection path |
| Immutable deploy artifact | Releases must be versioned and repeatable | One OCI image published to a registry and deployed by immutable reference |
| Deployment automation | Manual click-ops do not scale or audit cleanly | One CI/CD pipeline that builds, migrates, deploys, and verifies the single service |
| Config-as-code | Runtime settings and environment metadata need auditability | One repo-managed desired-state file set for runtime config and non-secret environment values |
| Health/log/error visibility | A live bot needs failure detection and restart/debug visibility | Health endpoint or equivalent liveness probe, structured logs, restart/error alerts |
| Backup/restore baseline | Persistent bot state must survive operator error or provider issues | Automated Postgres backups plus a documented restore check |
| Basic operator access control | Even without a public admin UI, repo/runtime access must be bounded | Provider IAM, protected repo branches, isolated CI secrets, and no public admin surface by default |

## 7. Later-phase components not required for initial Discord bot launch

| Component/capability | Why it can wait | What it unlocks later |

| `Kong API Gateway` | The bot does not need a public north-south API gateway to start | Public API ingress, identity propagation, and route governance |
| `FluxCD` continuous reconciliation | A single managed service can ship through simpler deploy automation first | Continuous reconciliation for richer multi-service or Kubernetes-based estates |
| `Crossplane` control plane | There is no initial requirement to synthesize cloud infrastructure from Kubernetes claims | Declarative multi-cluster/provider infrastructure management |

| `Platform Service` / `environment-manager-api service` | Dynamic environment creation is unrelated to launching one Discord bot | Ephemeral environment self-service and environment APIs |
| `Platform Deployer` | Claim-file generation and dynamic environment provisioning are out of scope for the first bot launch | Declarative environment instantiation from durable requests |
| `Debezium` | CDC-driven orchestration is heavier than required for one service | Durable change streams feeding other services and automation |
| `Kafka` | The initial bot can rely on Postgres and in-process/background execution | Shared async event bus for multiple services and alert pipelines |
| `Redis` deployment counters / aggregation layer | Deployment fan-in tracking is unnecessary for a single-service release | Faster transient aggregation and coordination once the platform grows |
| `Harbor` as dedicated self-hosted registry | The capability matters before the specific self-hosted product does | Full artifact governance and registry-side policy controls |
| `VictoriaMetrics`, `Elastic APM`, `Elasticsearch Anomaly Detection`, `StackStorm` | The bot needs baseline visibility before it needs a multi-backend AIOps estate | Full traces, anomaly detection, and automated remediation |
| `Calico`, `Linkerd`, `KEDA`, `Karpenter`, `Flink Adaptive Scheduler` | These are cluster-era networking and scaling components, not one-app managed-runtime blockers | Multi-service traffic policy, event-driven autoscaling, node scaling, and stateful workload scaling |
| `Trivy`, `Trivy Operator`, `Falco` | These are hardening layers, not prerequisites for the first managed bot launch | Supply-chain scanning, in-cluster security posture, and runtime anomaly detection |
