# Platform V2 Decomposition Index

## 1. Executive summary

This document specifies a full platform substrate for a Vultr-hosted Kubernetes environment, not a single service. It combines cloud bootstrap, GitOps control-plane installation, CI/CD, dynamic environment provisioning, identity and secrets, observability, alert automation, and autoscaling into one architecture. Its scope spans both management-cluster concerns and workload-cluster runtime behavior, with separate workflows for static production/staging promotion and API-driven ephemeral environments.

The spec assumes several lower layers or sibling specs already exist in enough detail to be implementable: a concrete identity and access-control design for Authentik, Pomerium, OPAL/Cedar, step-ca, and Infisical; a CI/CD and environment-management design for Dagger, GitLab, Debezium, and Kafka; workload definitions that Flux can deploy; and operational conventions for alerts, dashboards, and policies. In practice, this document acts as a composition layer over those subsystems. It provides the intended integration model and contracts, but many component-specific implementation details, failure modes, and lifecycle policies are left to other documents or to future work.

## 3. Architectural decisions

| # | Decision | Rationale | Scope | Confidence | Modernization risk |
|---|---|---|---|---|---|
| 1 | Standardize the platform on Vultr and VKE | Explicit stack choice: `"Cloud Provider: Vultr"` and `"Container Orchestration: VKE"` | Vultr, VKE, Terraform, Crossplane, Karpenter, object storage | HIGH | High vendor-lock risk; confirm current Vultr/VKE capabilities and API surface. |
| 2 | Treat security, developer velocity, and operational efficiency as co-equal top-level constraints | The goals are described as `"primary, non-negotiable objectives"` | Entire platform | HIGH | Low tooling drift risk, but downstream docs must not optimize one goal by violating another. |
| 3 | Use a single identity-driven control plane for all access paths | Explicit principle: `"single, identity-driven policy and control plane governs all access"` | Authentik, Kong, Pomerium, OPAL/Cedar, Infisical, observability | HIGH | Duplicates `auth-v5.md`; consistency matters more than re-specifying here. |
| 4 | Enforce zero trust and forbid network-location trust | Explicit principle: `"forbids trust based on network topology"` | Pomerium, Kong, networking, admin access workflows | HIGH | Conflicts with the bastion-host bootstrap pattern if that pattern remains. |
| 5 | Use JIT access with only short-lived credentials | Explicit principle: credentials are granted `"only at the moment they are needed"` | Pomerium, step-ca, SSH access | HIGH | Verify the step-ca-based JIT flow is still the preferred infra-access model in 2026. |
| 6 | Self-host the identity, secrets, and artifact-control stack | Explicit selections: self-hosted Authentik, Infisical, Harbor | Authentik, Infisical, Harbor, platform ops | HIGH | Self-hosting increases HA, patching, and backup burden. |
| 7 | Separate application access from infrastructure access with different gateways and credentials | Explicit `"Decoupled Trust Model"`; app JWTs must not grant infra access | Kong, JWT, Pomerium, step-ca, Authentik | HIGH | Must stay aligned with `auth-v5.md`; drift would create security gaps. |
| 8 | Make Authentik the exclusive identity source and sole OIDC provider | Explicit text: `"exclusive single source of truth"` and `"sole OIDC provider"` | Authentik, Kong, Pomerium, OPAL/Cedar, all users/services | HIGH | Strong coupling to one IdP; migration cost is high if this changes. |
| 9 | Require MFA for privileged identity flows | Explicit within Authentik definition | Authentik, user auth flows | HIGH | Implementation detail is not specified; verify enrollment and recovery design. |
| 10 | Use OPAL plus Cedar for universal fine-grained authorization and ABAC | Explicit choice: `"fine-grained decision engine"` and `"ABAC"` | Platform Service, downstream apps, data plane | HIGH | OPAL/Cedar ecosystem and policy authoring ergonomics may evolve. |
| 11 | Use Infisical as the only secrets store, accessed declaratively | Explicit text: `"centralized and exclusive store for all platform secrets"` | Infisical, all secret-consuming services, Kubernetes secret sync | HIGH | Operator/secret-sync behavior and HA model are underspecified. |
| 12 | Split provisioning into Day 0 Terraform, bootstrap Ansible, and Day 1+ Crossplane | Explicit `"phased process that transitions from imperative creation to declarative self-management"` | Terraform, Ansible, Helm, Crossplane, FluxCD | HIGH | Hand-off boundaries are complex and may be simplified during modernization. |
| 13 | Install FluxCD and Crossplane into a management cluster before delegating later lifecycle work | Bootstrap sequence explicitly seeds the control plane into the management VKE cluster | Management cluster, FluxCD, Crossplane | HIGH | Requires high confidence in management-cluster durability and upgrade path. |
| 14 | Use FluxCD to reconcile from Vultr Object Storage | Explicit integration: Flux `"monitor[s] a specific path within the Vultr Object Storage bucket"` | FluxCD, Vultr Object Storage, Platform Deployer | HIGH | Bucket-backed Flux sources are less common than Git-backed ones; verify 2026 support/fit. |
| 15 | Use a dual-model environment strategy: API-managed dynamic envs, Git-managed static envs | Explicit `"Dual-Model Environment Management"` goal | FastAPI, PostgreSQL, Debezium, Kafka, GitOps repo, FluxCD | HIGH | Overlaps heavily with `gitops.md`; boundaries need cleanup. |
| 16 | Implement dynamic environment provisioning as an asynchronous event-driven pipeline | Explicit FastAPI -> PostgreSQL -> Debezium -> Kafka -> Platform Deployer flow | Platform Service, PostgreSQL, Debezium, Kafka, Platform Deployer, Crossplane, FluxCD | HIGH | Missing rollback/compensation logic; also duplicated in `gitops.md`. |
| 17 | Use FastAPI and PostgreSQL as the control-plane API/data store for environment state | Explicit stack and endpoint definitions | FastAPI, PostgreSQL, Platform Service | HIGH | API payloads, quotas, and schema versioning are not specified. |
| 18 | Standardize CI execution on self-hosted GitLab Runner pods with Dagger-defined pipelines | Explicit stack and pipeline flow | GitLab, GitLab Runner, Kubernetes Executor, Dagger | HIGH | Validate whether self-hosted GitLab + Dagger is still the target CI stack in 2026. |
| 19 | Keep one portable pipeline definition for local and remote execution | Explicit text: `"identical whether run on a developer's laptop or in a GitLab CI job"` | Dagger, GitLab Runner, local dev workflows | HIGH | Dagger-centered portability may be stale if the org moved to another CI orchestrator. |
| 20 | Treat Harbor as the definitive source for both app images and infrastructure artifacts | Explicit text: `"definitive, self-hosted artifact repository"` | Harbor, Dagger, Platform Deployer, FluxCD, workloads | HIGH | OCI artifact contract and retention policy are not defined here. |
| 21 | Use a dedicated GitOps repository as the promotion boundary for static releases | Explicit flow where Dagger updates a separate repo and Flux consumes it | GitLab, Dagger, GitOps repository, FluxCD | HIGH | CI directly mutating `main` may not satisfy future change-control requirements. |
| 22 | Make local testing a high-fidelity simulation of the production GitOps loop | Explicit Kind + MinIO + local Harbor + local Flux workflow | Kind, MinIO, Harbor, FluxCD, Dagger, kubectl | HIGH | Local simulation cannot fully reproduce Vultr-specific networking or provider behavior. |
| 23 | Standardize north-south API traffic on Kong | Explicit stack choice and access-path description | Kong, JWT, FastAPI, downstream services | HIGH | Must remain aligned with `auth-v5.md` header/claim contracts. |
| 24 | Standardize east-west service networking on Linkerd | Explicit stack choice: `"Service Mesh: Linkerd"` | Linkerd, in-cluster service communication | MEDIUM | No rationale or integration detail is given; may be a soft selection rather than a defended decision. |
| 25 | Standardize observability on OpenTelemetry-enriched metrics, logs, and traces | Explicit `"Unified Observability"` goal and required attributes list | OpenTelemetry, Kong, Kafka, PostgreSQL, apps, observability backends | HIGH | Attribute coverage is strict, but implementation ownership is not assigned. |
| 26 | Use VictoriaMetrics for metrics and Elasticsearch plus Elastic APM for logs/traces | Explicit stack choice and use-case workflows | VictoriaMetrics, Elasticsearch, Elastic APM, Grafana, Kibana | HIGH | Elastic feature/licensing assumptions and long-term ops cost should be revalidated. |
| 27 | Normalize alerts onto Kafka and trigger remediation through StackStorm | Explicit AIOps model: `"central, durable alert bus"` and StackStorm rules/workflows | Kafka, vmalert, Elasticsearch anomaly detection, StackStorm | HIGH | StackStorm may be a modernization candidate if event automation standards changed. |
| 28 | Implement autoscaling as a layered chain: KEDA for workloads, Karpenter for nodes, Flink for stateful jobs | Explicit `"multi-layered"` strategy and causal-chain section | KEDA, HPA, Karpenter, Flink Adaptive Scheduler, Vultr | HIGH | Karpenter-on-Vultr and Flink-specific assumptions need current-state validation. |
| 29 | Expose declarative contracts through CRDs rather than only imperative APIs | Explicit CRD section for `VKECluster`, `InfisicalSecret`, and `ScaledObject` | Crossplane, Infisical, KEDA, Platform Deployer | HIGH | CRD versioning and compatibility policy are missing. |
| 30 | Enforce a default 24-hour TTL for `sue` environments, with teardown triggered by state removal | Explicit lifecycle workflow and use case | Platform Service, PostgreSQL, cleanup job, Debezium, Kafka, Crossplane, FluxCD | HIGH | Cleanup failure, exceptions, and user override policies are not specified. |
| 31 | Require peer-reviewed merge requests and immutable artifact tagging before production rollout | Explicit static deployment workflow | GitLab, Dagger, Harbor, GitOps repository, FluxCD, VKE | HIGH | Governance is partially undermined by the later direct GitOps-repo mutation step. |
| 32 | Use rolling updates as the standard release strategy for workload changes | Explicit `"zero-downtime rolling update"` target | FluxCD, VKE, kubelets, application deployments | HIGH | No canary/blue-green fallback or rollback criteria are defined. |
