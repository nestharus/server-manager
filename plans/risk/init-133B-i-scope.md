# INIT-133B-i — Scope risk gate

**Verdict:** LOW

## In scope (justified)

- **SPA Solid Router migration of `/`, `/applications`, `/admin/chapters` plus new `/applications/queue/`.** The current tree carries unmounted parallel scaffolding — `app/router.tsx`, `app/providers.tsx`, `RuntimeApp.tsx`, `features/public/HomeRoute.tsx`, `features/admin/AdminChaptersRoute.tsx` — none of which `index.html` loads, while the live entry `services/web/src/main.tsx` is 314 lines of vanilla DOM. AGENTS.md "no parallel systems" forbids leaving that limbo in place. The slice converts the parallel scaffolding into the real router and adds the queue route on top; no new routes sneak in beyond the three existing surfaces and the new `/applications/queue/`.
- **`ApplicationFormRoute.tsx` migration of the live applicant form.** Required because option B replaces `main.tsx`'s vanilla bootstrap; the applicant flow must continue to satisfy `compat.spec.ts` and e2e test 19. §3 "Applicant form DOM contract" pins the load-bearing selectors and auth-state semantics so the migration is a strict mirror plus one defensible tightening (auth-conditional rendering of tabs/details).
- **`/api/v1/web/officer/{applications,applications/{id}/claim}` bridge.** Load-bearing. The browser cannot supply trusted `X-Actor-*` headers; the core `/api/v1/applications` endpoints take `ActorIdentity` from a server-evaluated dependency. The bridge reads the Pomerium-asserted Discord snowflake, resolves it through `resolve_or_create_real_discord_member`, builds `ActorIdentity(actor_kind="user", actor_id=<member uuid>)` server-side, then calls `list_applications(...)` / `transition_application(...)` directly. Without it the queue + claim flow has no safe path from a Pomerium browser session to a core actor identity.
- **`me.py` adds `groups` and `discord_user_id` to `CurrentPrincipalRead`.** Load-bearing: the SPA must read `groups` to gate the officer UI surface, and the bridge must read both server-side. No additive parsing logic exists today.
- **Pomerium config additions: exact `path: /api/me`, exact `path: /applications/queue` + `prefix: /applications/queue/`, `prefix: /api/web/admin/`, `prefix: /api/web/officer/`, plus `idp_scopes += discord_user_id`, plus `jwt_claims_headers += x-pomerium-claim-discord-user-id`.** Each entry is the minimum required to gate the new page, the new bridge prefix, the principal probe, and the migrated admin chapters fetch path that `client.ts` switches to. The `/api/web/admin/` line additionally fixes a latent gap — the current config protects only the `/admin` page route, leaving `/api/web/admin/` to flow through the public catch-all — and is needed because the SPA migration repoints the admin chapters call to that prefix.
- **Authentik blueprint `init-133B-pomerium-officer-discord.yaml` declaring the `pomerium` OAuth2 app, `discord-pomerium` source, `server-manager-pomerium-discord_user_id` scope mapping, plus the `init-114-local-users.yaml` officer-group + Discord snowflake update.** The current `pomerium-config` already references `auth.local.humility.local/application/o/pomerium/` but no GitOps declaration exists. M1 from `research/20-init-133B-officer-identity-binding.md` requires emitting `discord_user_id` into the Pomerium token — that is the slice's identity binding, not separable.
- **`services/api/app/services/members.py` parameterization of `originating_actor` and `request_surface` on `resolve_or_create_real_discord_member`.** Load-bearing for audit correctness. Without it, first officer login attributes member-row creation to `actor_id="applicant-receipt"` / `request_surface="api:/api/v1/public/applications"`, which is misleading audit data. Parameterization defaults preserve the applicant call site exactly.
- **`_shared.py` (or rename to `etag.py`) folds `ApplicationListForbiddenError` mapping into `raise_known_application_error`; `lifecycle.py` updated to delegate.** The bridge needs `raise_known_application_error(...)` to map list errors with the same wire format as `/api/v1/applications/*`. Today that mapping is inlined at `lifecycle.py:106-110`; the bridge would either duplicate it (drift risk) or import a locally-mapped pattern. Folding is the minimum refactor that keeps wire format aligned across both surfaces.
- **Deletions: `RuntimeApp.tsx`, `DarkNemesisForm.tsx`, `features/forms/schema.ts`, `features/forms/form.module.css`.** `RuntimeApp.tsx` is the second unmounted runtime AGENTS.md "no parallel systems" forbids. `DarkNemesisForm` is a demo form whose only consumer is `HomeRoute.tsx`; once `HomeRoute` is repointed to mirror the live public route, the demo form has zero callers and `schema.ts` / `form.module.css` are orphaned — these are not "while we're at it" deletions, they fall out of the migration and are required to leave no parallel-form surface behind.
- **New tests: `officer-queue.spec.ts`, `test_web_officer_applications.py`, extensions to `test_applicant_discord_blueprint.py`, `test_applicant_discord_pomerium.py`, `validate_web_ui_local.sh`, `19-web-ui.sh`, `browser-flow.mjs`, `seed-authority-grants.mjs`.** Each test exercises code this slice ships, plus the locked-actor server-side dependency-tree check, the `client.ts` `/api/v1/...` negative-grep guard, and the `/applications/queue` route-collision assertions. None audit pre-existing systems beyond the minimum needed to lock the slice's contract.

## Splittable concerns

- **The SPA Solid Router migration is the most splittable component.** It could in principle be a precursor INIT that lands the router as the live entry, deletes `RuntimeApp.tsx` / `DarkNemesisForm.tsx`, and migrates `/`, `/applications`, `/admin/chapters` onto Solid without touching identity, Pomerium, or backend. The bundle is justified here because (a) the parallel scaffolding already violates AGENTS.md and is overdue for removal, (b) a migration-only INIT ships no observable feature, making its correctness harder to validate and prioritize, (c) bundling forces the migration to land in service of a real route, and (d) §9 already encodes the right escape hatch — "if implementation exceeds the prior `+1,250` ceiling or touches unrelated backend services, the scope gate should fail and split the TanStack Solid Router migration from the queue route." Given the locked diff budget is `+1,060 / -260`, the bundle stays under that ceiling.
- **The web-officer bridge is NOT separately splittable.** The two endpoints exist only to serve this slice's UI; their request/response shapes, error mapping, and identity binding are co-designed with the queue + claim flow. Shipping the bridge ahead of the UI would land an unused server surface.
- **The Pomerium config update is NOT separately splittable.** Each new route entry serves a path the slice introduces or repoints; landing them ahead of the slice would gate routes that don't yet exist.
- **Member-service parameterization is NOT separately splittable.** Defaults preserve the applicant flow exactly; the new params have no caller until the bridge ships, and the bridge cannot ship without them without leaking the applicant-receipt actor into officer audit records.
- **The `_shared.py` → helper migration of `ApplicationListForbiddenError` is a pure refactor.** Step 1 of §3 carves it as an explicit prerequisite ("must land first") with its own unit test, which is the right discipline; it is technically ahead-of-bridge work but small enough that a separate INIT would be heavier than the change itself.

## Verdict reasoning

LOW. The proposal is materially larger than INIT-133A's "one repository function + one endpoint + one contract" because INIT-133B-i is the first authenticated officer surface — it must concurrently bind a new identity claim, build a server-side actor bridge, gate new HTTP paths at the edge, and resolve a pre-existing parallel-scaffolding violation that AGENTS.md requires removed before more SPA features land on top of it. Each expansion is load-bearing for the slice (bridge, Pomerium routes, Authentik blueprint, member-service parameterization, deletions of unmounted parallel runtimes) or a forced AGENTS.md correction whose result this slice is the first real consumer of (the SPA migration). The proposal's anti-scope is explicit and correctly excludes detail/transcript/messaging/decision/scope-selector/schema/permission work; the diff budget includes a hard fail-condition that splits the migration if it grows past the prior ceiling. The migration is the only genuinely splittable concern, and the proposal already acknowledges that exact split as the fallback. No "while we're at it" cleanups or pre-existing-system audits sneak in: every modified backend file, every Pomerium route, every test, and every deletion ties back to a specific slice requirement.
